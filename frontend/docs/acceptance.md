# Итоговая приёмка F31

## Автоматическая проверка

Из корня выполните `VITEST_MAX_WORKERS=2 ./scripts/frontend-checks.sh`, затем из frontend `npm run test:acceptance`. Последняя команда выбирает поставки, заказы, списания, редакторы продукта/блюда, вход, права, SSE, сохранение форм при фоне, русский календарь и дополнительные 413/429/5xx сценарии. Для всей матрицы экранов используйте `npm run test:browser`. Все эти browser-сценарии используют явный MSW и не обращаются в БД приложения.

Настоящая production-сборка проверяется отдельно:

```sh
# Один раз установите goose v3.27.1 и Chromium; Docker должен работать локально.
go install github.com/pressly/goose/v3/cmd/goose@v3.27.1
cd frontend
npx playwright install chromium
npm run test:production
```

`tests/production/run.sh` создаёт случайно названный Compose project, loopback-порты, tmpfs PostgreSQL и случайные тестовые пароли в защищённом временном каталоге. Применяет миграции и обычный seed-users; начальная singleton-настройка — существующая demo fixture. Продукты, рецепты, поставки, заказы и списания создаются через опубликованный API. Dockerfile backend/frontend и nginx берутся из инфраструктуры без изменений. Traefik v3.7 использует такие же timeout/flush settings через file provider без Docker socket. Между независимыми сценариями тест даёт две секунды на восстановление серверного bucket (10 запросов/с, burst 20), сохраняя реальный rate limit включённым. Проверочные GET допускают до двух повторов по Retry-After при 429; записи не повторяются автоматически. Cleanup удаляет только ресурсы этого project и сгенерированные образы. Никогда не комбинируйте тестовый Compose с deployment-конфигурацией.

Production-конфигурация не запускает Vite и MSW. Проверяются:

1. Настоящий login через Traefik/nginx, HttpOnly/SameSite cookie, успешные CSRF записи и отказ при отсутствии CSRF, native SSE и доставленное inventory.changed.
2. Приёмка четырёх партий трёх ингредиентов, заказ двух Маргарит и split-FEFO расход теста из двух партий. Текущие балансы и движения сверяются с настоящим API.
3. Потеря уже успешного серверного ответа для поставки, заказа и ручного списания: Playwright пропускает запрос в backend и затем обрывает ответ. UI повторяет тот же ключ и тело; список/ledger содержит единственную запись. Приёмка дополнительно переживает reload.
4. Полное списание томатов обновляет стоп-лист/закупки; недостаток запрещает оформление в UI. Независимый итоговый POST получает 409; остатки всех ингредиентов и число движений не меняются, корзина остаётся заполненной.
5. Четыре реальные роли, запрещённые прямые ссылки без бизнес-запросов, logout/401, reload вложенных путей, ширины 360/390/1024/1440. Истечение сохраняет черновик прежнего владельца; вход другого пользователя не раскрывает его.

Тесты сохраняют только безопасные скриншоты; нет traces, video или файлов с credential headers. Ошибки/конфликты/медленная сеть и рецептура между check/submit дополняются существующей MSW-матрицей. Отказ 413 разблокирует исправление; 429/5xx сохраняют неопределённую попытку для явного точного повтора. Начальная загрузка без кеша проверяется отдельно от фона. Смена синтетической рецептуры после успешного check до POST требует явного подтверждения нового состава; корзина сохраняется. Это не имитация серверной транзакционной проверки.

CI запускает оба вида приёмки и полный frontend gate независимо от backend CI S27. Локальная проверка workflow не означает, что удалённый GitHub job уже выполнен: push не является частью этой задачи.

## Ручная демонстрация с seed и demo-events

Подготовьте **выделенную demo-установку** по [инструкции инфраструктуры](../../infrastructure/README.md#seed-и-сброс-demo-окружения), задайте четыре `DEMO_*_PASSWORD` вне репозитория и выполните `task seed`. Обычный seed не удаляет пользовательские данные и не освежает сроки существующих партий. Для воспроизводимого нового прогона используйте новую demo-БД или отдельно подтверждённый demo-reset; не сбрасывайте рабочий склад.

1. Войдите `manager@flagman.invalid` со своим demo-паролем. Приёмка: добавьте «Моцарелла», «Томаты», «Тесто для пиццы» с актуальными сроками. Разделите тесто на две партии с различными сроками, чтобы показать FEFO.
2. Откройте детали поставки → выбранные партии склада. Создайте две порции «Пицца «Маргарита»». Покажите проверку всей корзины, серверные фактические списания, историю заказа и текущие балансы.
3. В отдельной demo-партии спишите оставшиеся томаты с причиной. Покажите историю движения, стоп-лист и закупки. Попытка большего заказа сохраняет корзину без частичного расхода остальных продуктов.
4. В соседней вкладке или терминале запустите ограниченный поток обычных API событий. Получите `DISH_ID` Маргариты из опубликованного `/dishes` и используйте точные origin своей demo-установки:

```sh
# DEMO_MANAGER_PASSWORD наследуется из вашего защищённого окружения.
ENV=demo task demo-events CONFIRM=demo \
  DEMO_URL=http://flagman.localhost ORIGIN=http://flagman.localhost \
  DISH_ID=<uuid> SCENARIO=replenishment COUNT=2 INTERVAL=1s
```

Повторите с `SCENARIO=normal` или `depletion`, ограничив COUNT. Адрес должен вести к выделенной demo-базе; `ORIGIN` должен точно совпасть с `FRONTEND_ORIGIN`. Эти команды создают настоящие поставки/заказы. Клиент не знает, какая БД стоит за HTTP; не направляйте его на production. Наблюдайте обновление активного склада/стоп-листа и сохранение незавершённой формы. Grafana, если нужна техническая диагностика, открывается отдельно.

## Граница подтверждённой интеграции

Изолированная приёмка подтверждает frontend production bundle + существующий nginx + Traefik с теми же timeout/flush settings + реальный backend/PostgreSQL на HTTP. HTTPS Secure cookie, внешнюю конфигурацию ingress, worker time markers/auto-writeoff и долговременный SSE replay конкретной установки требуют отдельной deployment-проверки. MSW не доказывает эти свойства. Не используйте production credentials в тестах.
