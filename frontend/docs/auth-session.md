# Вход и жизненный цикл сессии (F03)

`/login` содержит React Hook Form + Zod: email, обязательный пароль без новой политики сложности, показ/скрытие, фокус первой ошибки, блокировка повторной отправки, безопасные сообщения 401/403/429 и ожидание Retry-After (секунды или HTTP-date). После любой попытки пароль очищается. Пароли не входят в Redux actions, RTK Query, URL, логи и browser storage. Автоматическое заполнение `current-password` остаётся доступным менеджеру паролей браузера.

## Плановый контракт и draft-адаптер

Источники: раздел «Эндпоинты входа» корневого README, `backend/docs/api.md`, `backend/docs/openapi.yaml`. README описывает плановые поля; api.md прямо отмечает, что выдача сессий login/me/logout ещё не реализована. В OpenAPI этих операций и схем пока нет. Реальный серверный контракт и интеграция ожидают S15. Backend не изменяется.

Все пути, wire-схемы Zod и преобразования в модель frontend сосредоточены в `frontend/src/features/auth/api/draft-auth-adapter.ts`. Для замены на опубликованный контракт не требуется менять форму или SessionController. Используются описанные README пути и поля:

| Запрос | Плановый обмен |
|---|---|
| POST `/api/v1/auth/login` | `{email,password}` → `{user,csrf_token,session_expires_at}`; cookie выдаёт сервер |
| GET `/api/v1/auth/me` | `{user,csrf_token,session_expires_at,settings}` |
| POST `/api/v1/auth/logout` | Без тела, `X-CSRF-Token`, ответ 204 |

`user`: id, name, email, role, is_active, revision, created_at, nullable last_login_at. `settings`: restaurant_name, timezone, expiring_threshold_hours, auto_writeoff_expired, revision. При входе сначала проверяется login-ответ, затем вызывается me для загрузки settings и проверки того же пользователя. Доступ открывается только после обоих ответов. Проверяются активность пользователя, срок сессии, IANA timezone и формат ответа. JSON cookie и пароль не сохраняются; CSRF хранится отдельно в памяти, вне Redux.

Адаптер выполняет запросы напрямую с `credentials: include`, общим форматом ErrorResponse и таймаутом 15 секунд. Это сознательно исключает сохранение login-аргумента в RTK Query/Redux. Автоматических повторов мутаций нет. Сообщения сервера и произвольные error.details не показываются на форме: используются локальные безопасные сообщения.

## Восстановление и очистка

Все рабочие разделы защищены SessionGate. После загрузки выполняется один me; параллельные запросы ожидают общую попытку. Ошибка связи показывает повторную проверку, не открывая домашний экран. Shared API получает порты из app; все бизнес-запросы ждут доступа, healthcheck остаётся публичным. 401 бизнес-запроса очищает сессию и переводит защищённый маршрут на login. Смена поколения сессии отбрасывает старые ответы. SessionGate включает таймер истечения на защищённом экране; просроченный известный срок также проверяется перед бизнес-запросом. После асинхронного ожидания доступ проверяется ещё раз, чтобы logout между microtasks не пропустил запрос.

returnTo принимает только внутренний путь. Внешние адреса, неоднозначные encoded пути, обратные слеши и login-циклы отклоняются. Query и hash удаляются, чтобы секреты из URL не переносились на login. F04 проверяет returnTo по единой матрице прав и выбирает доступный раздел; все текущие роли имеют доступ к обзору. См. [навигацию](navigation.md).

SessionGate не подключается к публичным `/dev/ui` и `/dev/api`, доступным только в dev. Они по-прежнему позволяют проверять UI и транспорт без рабочего auth backend.

`saveWorkDraft({key,draft})` из entities/session сохраняет только `title` и `note` в памяти, с owner ID. Будущие формы должны передавать только несекретные поля этого allowlist. При истечении сессии черновики временно недоступны защищённым экранам; повторный вход того же пользователя возвращает их. Другой пользователь и явный logout очищают их. Перезагрузка вкладки не сохраняет черновики; постоянное хранение произвольных форм не добавлено. `replaceBasket` — базовое состояние строк будущей корзины; оно очищается при выходе/истечении. Экраны корзины относятся к последующим историям.

Кнопка выхода F04 сначала проходит router blocker изменённой формы через /logout; после подтверждённого перехода выход очищает пользователя/settings, черновики, корзину и CSRF, отменяет активные query/mutation и сбрасывает RTK Query. `registerSubscription(close)` контроллера позволяет будущим SSE подпискам участвовать в очистке; один неисправный disposer не препятствует остальным. Запоздавшие login/me/бизнес-ответы не возвращают данные старого пользователя. Если сервер не подтвердил logout, UI явно сообщает о локальной очистке и неподтверждённом отзыве cookie. После перезагрузки серверная cookie может снова восстановить сессию; подтверждение отзыва проверяется отдельно с реальным S15.

## Явная проверка MSW

`VITE_ENABLE_MOCKS=true npm run dev`. Production игнорирует этот флаг и всегда отправляет реальные запросы; подмена после 404/ошибки отсутствует. Панель «Моковый режим» открыто обозначает тестовые ответы. В локальном mock-режиме: email `employee@example.test`, пароль `local-test-only` (исключительно fixture, не production credential). Mock-cookie `flagman_mock_session` специально читается JavaScript и моделирует reload; это не проверка HttpOnly/Secure/Origin реального сервера.

Сценарии: успешный/медленный вход, неверный пароль, отключённый пользователь, нет/истекла сессия, 429, сетевой/серверный сбой, неверная структура. Переключение фиксируется на попытку; неизвестные API остаются MOCK_NOT_IMPLEMENTED и не обращаются к реальному складу.

Проверки: `./scripts/frontend-checks.sh`; `npm run test:browser` в frontend. Playwright явно включает MSW для своего локального Vite, проверяет 360/390/1024/1440 px, Tab/Space, валидацию, pending, ошибки, reload и logout. Unit-тесты дополнительно проверяют 401-барьер, CSRF, отсутствие повторов, черновики/смену пользователя, очистку подписок и поздние ответы. Эти результаты проверяют frontend; реальные session cookie, CSRF/Origin и серверный отзыв сессии ожидают S15.
