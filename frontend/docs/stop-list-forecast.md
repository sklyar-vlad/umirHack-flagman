# Прогноз стоп-листа (F29)

`/analytics/stop-list-forecast` и совместимый `/forecast` доступны admin/manager.
GET использует опубликованный StopListForecastListResponse без изменений backend.
URL содержит только lookback_days (1–90, default 7), horizon_hours (1–720, default 72), page и page_size (1–100, default 50). Неверные/повторяющиеся значения не отправляются; форма показывает ошибки. Изменение настроек сбрасывает страницу; back/reload сохраняют URL. Сортировку estimated_stop_at ASC NULLS LAST задаёт сервер, frontend не пересчитывает и не переставляет строки.

Карточка показывает серверное dish_name, причину, estimated_stop_at в зоне ресторана, limiting_product_id, confidence и допущения. Точный RFC3339 сохраняется в time datetime/title. already_unavailable означает недоступность в server_time; expiry и estimated_demand разделены. insufficient_data и missing_history обозначают неизвестный спрос в текущей единице. Даже при известной дате expiry эта оценка не учитывает неизвестный расход. null с no_stop_within_horizon означает только отсутствие найденной остановки внутри горизонта; unknown_demand_no_expiry_stop_within_horizon означает недостаток истории и отсутствие остановки только по срокам. Ни одно состояние не обещает вечную доступность. Неизвестные допущения отображаются безопасным текстом, без HTML.

Будущие поставки не предполагаются и не добавляются автоматически. Никаких order/check, резервов или записей. Для admin ссылки ведут к существующим редакторам блюда/продукта; manager получает разрешённый маршрут рецепта `/dishes/:id` (существующий экран раздела). Контракт не публикует имя ограничивающего продукта: показан его UUID, без выдуманного поиска склада или дополнительных запросов.

Ответ проверяется до cache: DTO, даты с зоной, safe pagination, уникальные dish IDs, соответствие page/page_size и параметров meta. currentData изолирует настройки. Ошибка того же запроса оставляет явно устаревший снимок; 403 скрывает его. Mount/focus/reconnect, visible polling 30 с и StopListForecast invalidation после поставки/заказа/списания/редактирования продукта или рецепта обновляют активные подписки.

MSW включается только явно в development/test. forecast-demo и обычный сценарий содержат иллюстративные серверные DTO для уже недоступного блюда, expiry с неизвестным расходом, estimated_demand, недостатка истории и no_stop_within_horizon. Это не реализация модели прогноза на клиенте; параметры отражаются в meta, синтетический расчёт FEFO/спроса не заявляется. Есть empty/slow/error/forbidden/invalid сценарии. Production использует реальные запросы. Проверки frontend/MSW не подтверждают настоящий S23: authenticated чтение, server FEFO и история расхода остаются отдельной интеграционной проверкой.
