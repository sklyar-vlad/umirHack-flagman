# Пользователи и роли

F21: `/admin/users` доступен только admin. `GET /users` и `GET /roles` используют опубликованные схемы из `backend/docs/openapi.yaml` и описание S16 в `backend/docs/api.md`. Список показывает имя, email, русское название роли, активность и последний вход. `last_login_at: null` означает «Ещё не входил»; время форматируется в `settings.timezone`, а не в часовом поясе браузера.

URL хранит только `search`, `role`, `is_active`, `sort=name`, `page`, `page_size`. По умолчанию все роли/активности, страница 1 и 50 записей, максимум 100. Поиск отправляется как буквальная часть имени/email; `%`, `_` и обратный слеш сохраняются. Смена фильтра/размера возвращает первую страницу, история браузера восстанавливает состояние. На пустой дальней странице есть возврат к первой.

Опции ролей приходят из `GET /roles`, который должен вернуть четыре уникальных опубликованных кода. Новые редактируемые роли не создаются. При ошибке справочника отображается отдельная ошибка с повтором, фильтр ролей отключён, а подписи записей используют фиксированные русские названия из существующей матрицы доступа. При 403 любого из двух GET скрываются и ранее загруженные пользователи. При временной ошибке списка сохраняется только снимок для тех же параметров с предупреждением об устаревании; новый набор параметров не показывает старый список. Список и справочник обновляются при монтировании, фокусе/восстановлении сети и соответствующей инвалидации `Users`/`Roles`.

Строгая схема `AuthUser` принимает только безопасные опубликованные поля: `id`, `name`, `email`, `role`, `is_active`, `revision`, `created_at`, `last_login_at`. Пароль, хеш и токены не запрашиваются и не отображаются; ответы с дополнительными полями отклоняются до попадания в RTK Query cache. Пользователи не сохраняются в storage. Общий транспорт ждёт восстановления сессии и очищает API cache при смене/завершении сессии.

«Создать пользователя» ведёт на `/admin/users/new`, редактирование — `/admin/users/:id/edit`, сброс пароля — `/admin/users/:id/password`. Совместимый `/admin/users/:id` тоже открывает вход редактирования. Все переходы защищены тем же admin guard и сохраняют разрешённые фильтры возврата. F22 заменяет входные страницы рабочими формами и диалогом смены пароля. `/password` открывает тот же диалог после свежего чтения пользователя. Email-приглашения и рассылка не отправляются.

Разработка и тесты используют только явный `VITE_ENABLE_MOCKS=true`; новые сценарии расширяют общий MSW. Синтетические DTO и фиктивные адреса `example.test` не являются реальными пользователями. Production использует реальные запросы без fallback на моки. S16 обозначен в документации backend как implemented, но эти проверки подтверждают только frontend: интеграция с реальной сессией, RBAC и серверным снимком отдельно не проверена. Подтверждённые изменения F22 инвалидируют `Users`, включая детали и активный список.

## Создание, доступ и пароль (F22)

Формы используют опубликованные `CreateUserRequest`, `UpdateUserRequest`, `UserPasswordRequest`. При создании поле формы «Начальный пароль» преобразуется из локального `initial_password` в контрактное `password`; не отправляется поле `initial_password`. Имя обрезается по краям и проверяется на 1–200 Unicode-символов без управляющих символов; email обрезается, приводится к нижнему регистру и ограничивается 254 байтами. Пароль не обрезается: 12–128 Unicode-символов. Роли выбираются только из опубликованного справочника. Ошибка/загрузка справочника блокирует сохранение.

Редактирование начинает отдельное свежее `GET /users/{id}`. Форма владеет снимком и `expected_revision`; инвалидация, фокус и восстановление сети не заменяют его или введённые значения. PATCH содержит только изменённые поля и ожидаемую ревизию; пароль не входит в PATCH. Изменение роли/активности требует подтверждения. Последний активный admin защищается сервером (`LAST_ADMIN_PROTECTED`); `CONFLICT` email и 422 сохраняют введённые данные. Тексты серверных ошибок не отображаются напрямую, пути полей ограничены разрешённым набором.

`REVISION_CONFLICT` блокирует отправку. «Прочитать актуального пользователя» загружает текущий снимок; пользователь сравнивает его со своими сохранёнными значениями и явно нажимает «Продолжить с этой ревизией». Чтение само ничего не сохраняет. 403/404 и ошибка чтения не разрешают отправку. При потере ответа или некорректном успешном DTO исход неизвестен: повторный submit запрещён, создание требует проверки списка, редактирование — явного чтения/проверки перед новой попыткой. Автоматического повтора нет.

Пароль передаётся отдельным закрытым thunk, который использует общий cookie/CSRF/session transport. Замыкание, а не сериализованный action, содержит запрос: секрет не попадает в Redux, аргументы/кэш RTK Query, persistent drafts, storage или логи. Весь пользовательский черновик остаётся только в памяти формы. Успешный ответ проверяется строгой безопасной схемой и на соответствие отправленным полям, ID и следующей ревизии; из ответов ошибок допускаются только фиксированные коды и пути с безопасными локальными сообщениями, без отражённых значений.

Диалог предупреждает об отзыве всех сессий. Пароль очищается после успеха или явного закрытия; Escape с непустой формой запрашивает подтверждение очистки. Модальное окно удерживает клавиатурный фокус и возвращает его на кнопку. Повторный submit блокируется на время запроса. Уход с изменённой формы требует подтверждения, во время сохранения уход блокируется.

Смена роли, отключение и пароль отзывают сессии; включение их не восстанавливает. После подтверждённого изменения своего доступа/пароля текущая сессия завершается локально и открывается login; транспорт также обрабатывает серверный 401. Изменение только собственного имени/email сохраняет сессию и обновляет её безопасную идентичность. MSW моделирует те же операции на синтетических записях, включая конфликты, 422, медленный запрос и потерю ответа. Эти сценарии не подтверждают реальные серверные блокировки, Argon2id, аудит или отзыв cookie-сессий.
