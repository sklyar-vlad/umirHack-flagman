# Заказы: история, оформление и детали (F09–F11)

`/orders` доступен admin, manager и order_operator по общей матрице ролей. Кладовщик не монтирует экран и его запросы. Две вкладки читают опубликованные `GET /api/v1/orders` и `GET /api/v1/order-attempts` из `backend/docs/openapi.yaml` / `backend/docs/api.md`. Только активная вкладка подписана на запрос; возврат на неё обновляет данные.

Успешные заказы показывают номер, дату, автора, состав, версии рецептур, порции и статус completed. Названия берутся исключительно из исторических `items[].dish_name`; текущий каталог блюд не запрашивается. У сохранённых отказов — собственный UUID, reason_code и исторический состав, без номера/ссылки успешного заказа. Раскрытие показывает точные decimal-количества required/available/missing/expired, причины просрочки и issues из снимка. Эти количества не означают текущий остаток.

## URL и период

`tab=attempts` выбирает отклонённые попытки; отсутствие — успешные заказы. Поля каждой вкладки именованы `orders_search/from/to/page/page_size` и `attempts_search/from/to/page/page_size`; `attempts_reason_code` — INSUFFICIENT_STOCK, RECIPE_CHANGED или DISH_UNAVAILABLE. Пример: `/orders?tab=attempts&orders_page=2&attempts_reason_code=RECIPE_CHANGED`. Изменение фильтра сбрасывает только активную страницу. Сброс не очищает другую вкладку. Back/Forward, reload, вход и returnTo сохраняют обе вкладки.

В API передаются только опубликованные без префикса вкладки параметры активной вкладки, включая `sort=-created_at`, page и page_size; пустые необязательные параметры отсутствуют. reason_code никогда не отправляется в GET /orders. Поиск — буквальная подстрока номера/UUID либо исторического названия блюда, без локального переименования/фильтрации ответа. Пагинация использует total сервера.

Период `[from,to)` ограничивает created_at. RHF/Zod преобразует datetime-local через явный settings.timezone (по умолчанию Europe/Moscow), независимо от браузера. Точные границы и неизменённые дробные секунды сохраняет общий `shared/lib/history`; поставки используют тот же модуль через существующий публичный API. Неверный период/reason в URL не запускает запрос; пользователь может сбросить фильтры. DST-пропуск/неоднозначность не исправляются молча.

## Состояния и переходы

Вкладки поддерживают загрузку, пустую историю, отсутствие результатов, страницу за total, retry и локальный 403. При сетевой ошибке обновления остаётся последний успешный ответ только для текущего набора параметров с явной подписью об устаревании. Новые параметры не показывают предыдущий список. 403 скрывает cached records без завершения сессии.

Клавиатура: Tab входит в активную вкладку; стрелки, Home/End меняют вкладку и фокус. Нативные details раскрываются Enter/Space. Общий UI-kit показывает таблицу на desktop и карточки до 1100 px; контрольные ширины 360/390/1024/1440.

Номер заказа ведёт на защищённый `/orders/:id`, разрешённая кнопка — на `/orders/new`. F09 обеспечивает входные экраны и очищенный возврат в историю. F10 заменяет вход нового заказа полноценным оформлением и показом фактических списаний после успеха. F11 предоставляет отдельное чтение деталей `/orders/:id`. Сама история не отправляет POST /orders или /orders/check.

История читается с сервера и никогда не пополняется локально при сетевой/технической ошибке, предварительной проверке или отказе доступа. Только серверный OrderAttempt является сохранённым предметным отказом.

## Проверки и интеграция

`./scripts/frontend-checks.sh` и `cd frontend && npm run test:browser` проверяют frontend. MSW включается явно через VITE_ENABLE_MOCKS=true только в development/test; production всегда использует реальные запросы. order-handlers расширяет существующие success/slow/network-error/forbidden/error сценарии и orders-empty. Fixtures включают исторические названия, три причины, дефицит, точные границы и отдельную пагинацию.

Компонентные тесты проверяют оба контракта/списки/ошибки, отсутствие inactive запросов и неизменную историю после тестовой предварительной проверки. Браузерные тесты проверяют session/role routing, URL, keyboard, responsive, loading/retry/403 и снимки. Это не проверка реальных S11/S15, серверной сохранности отказов, SQL-снимков, cookie/RBAC или CSRF. Интеграция с выключенными mocks остаётся отдельной проверкой; текущий изолированный auth adapter также требует сверки с опубликованным контрактом.

## F10 — новый заказ

`/orders/new` содержит каталог с буквальным поиском и составом на порцию, доступностью сервера и общей корзиной. Отдельная страница меню не добавляется. `frontend/src/features/compose-order/index.ts` экспортирует `addBasketDish`: будущая рекомендация добавляет опубликованный Dish тем же помощником в `session.drafts.order.order`, через `saveWorkDraft({ key: 'order', draft: { order: next } })`. `session.basket` — проекция целых валидных порций этой общей корзины, без независимого второго состояния. Одинаковые dish_id объединяются; лимиты — 100 блюд и 1000 порций каждого. Невалидные значения сохраняются для исправления, но не отправляются.

Принятый снимок рецептуры хранится в корзине. Замена состава/версии/активности требует видимого подтверждения пользователя. Новые детали читаются через GET `/dishes/{id}`; более ранняя revision не перекрывает свежую. Неудача загрузки не разрешает подтверждение. После подтверждения отключённого блюда оно остаётся в корзине и требует удаления, без ложного успешного check.

POST `/orders/check` выполняется через 300 мс, без Idempotency-Key. Старый запрос отменяется, а его результат игнорируется. Ответ дополнительно сверяется с dish_id/порциями и, для can_create, с версиями. Состояние связано с точным снимком корзины и локальной ревизией редактирования: любое изменение сразу отключает оформление. Общие requirements/shortages и can_create берутся у сервера. Доступные порции отдельных блюд не суммируются. Check ничего не резервирует и не создаёт историю отказов.

Перед POST `/orders` сохраняется неизменная пара UUID Idempotency-Key и OrderRequest с проверенными recipe_version. Двойной submit блокируется синхронно. Сеть, таймаут, 5xx, неверный ответ, REQUEST_IN_PROGRESS, конфликт ключа, 401/403 и 429 сохраняют попытку: отказ транспорта/доступа на повторе мог произойти до чтения уже сохранённого результата. Пока результат неизвестен, редактирование блокируется и доступен только точный повтор. Retry-After учитывается для 429; безопасный повтор ограничен 23 часами при опубликованном минимуме хранения ключей 24 часа. После этого UI требует проверки истории ответственным сотрудником, не выдавая новый ключ.

Предметные 409 отображают только валидированные серверные attempt_id/requirements/shortages/issues. Они сохраняют корзину, требуют новой проверки и нового ключа для новой попытки. RECIPE_CHANGED и DISH_UNAVAILABLE требуют загрузки и подтверждения актуального состава. 422 показывает опубликованные индексированные ошибки исходного запроса и сохраняет введённые данные. Ошибки сети и check не изображаются как сохранённый предметный отказ.

Несекретный черновик и исходная попытка сохраняются в sessionStorage только для владельца, восстанавливаются после аутентификации, переживают истечение сессии и reload того же пользователя, удаляются при logout/смене пользователя. CSRF и credentials не сохраняются. Подтверждённый OrderDetail сверяется с исходными блюдами/порциями/версиями; только затем корзина очищается. Экран успеха показывает серверный номер, позиции, recipe_version и реальные allocations с batch_id, supply_id, строкой поставки, списанным количеством и остатком после движения. Ссылки ведут к заказу и выбранным партиям склада.

Создание/финальная неудача инвалидируют историю успехов/отказов, склад, партии, каталог и зарегистрированные теги рекомендаций/стоп-листа; они не выдумывают новые записи в клиентском кеше. Дальнейшие экраны должны использовать уже предусмотренные теги Dishes, Inventory, Batches, Orders, OrderAttempts, Procurement, StopList, HotOffers.

Сценарии `dishes-*`, `order-check-*`, `order-submit-slow`, `order-network`, `order-lost-response`, `order-shortage`, `order-recipe-changed`, `order-inactive`, `order-final-*`, `order-validation`, `order-rate-limit` расширяют явный MSW development/test режим. Синтетический общий запас и списания по годным партиям используются только для frontend-проверок. Они не проверяют SQL/FEFO/транзакции, реальные cookie/CSRF/RBAC или конкуренцию серверных заказов. Production использует реальные запросы; интеграция с S08–S11/S15 остаётся отдельно непроверенной.


## F11 — фактическое списание по заказу

Защищённый `/orders/:id` читает только опубликованный GET `/api/v1/orders/{id}` без query-параметров. Ответ валидируется схемой OrderDetail и сверяется с запрошенным UUID. Неверный UUID не отправляется. Экран использует сохранённые названия, автора, дату в timezone ресторана, порции, recipe_version и каждое движение allocations. Запросов `/dishes/{id}` нет: изменение текущей рецептуры не меняет исторический состав. Две партии одного продукта показываются отдельно, в порядке сервера, с batch_id, supply_id, номером/строкой поставки, точным количеством и единицей. Остаток после движения явно обозначен историческим, а не текущим складским остатком.

Тот же OrderSnapshot используется после создания F10. Обновление при входе/возврате и кнопкой читает текущий ID; переход между ID не показывает предыдущий ответ. Загрузка, ошибка первой загрузки, клавиатурный retry и последняя успешная версия при временной ошибке имеют отдельные состояния. 404 и 403 скрывают кешированный снимок; 404 означает отсутствующий ресурс, 403 не завершает сессию.

Возврат использует allowlisted returnTo и сохраняет фильтры обеих вкладок истории. Ссылка на склад передаёт product_id и буквальный поиск по сохранённому названию. Только admin/manager получают supply_id и панель всех партий из выбранной поставки; order_operator не запрашивает запрещённые поставки. Права берутся из общей матрицы ролей. Десктопная таблица заменяется карточками до 1100 px, UUID переносятся без горизонтального переполнения.

Явные MSW-сценарии order-detail-demo/order-detail-split показывают 240 г моцареллы, 200 г томатов и 2 шт. теста; split разделяет моцареллу на 120,001 и 119,999 г. Связанные синтетические SupplyDetail/Inventory/Batch доступны только в этих сценариях и позволяют проверить переход к складу, включая израсходованную партию. Это фиксированный тестовый складской снимок, не алгоритм восстановления реального остатка из истории. order-not-found проверяет ресурсный 404. Детали F10-созданных синтетических заказов читаются из общего mock state. Производственные запросы остаются реальными.

Компонентные и браузерные проверки покрывают все ингредиенты/партии, дробные количества, версии каждой позиции, фильтры, роли, keyboard, ошибки, запоздалый ответ другого ID, 360/390/1024/1440 px. Проверки MSW не подтверждают реальную S11-интеграцию, неизменность SQL-снимков, cookie/CSRF/RBAC; это отдельная проверка с выключенными mocks.
