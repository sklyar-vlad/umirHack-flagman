# История поставок (F06)

`/supplies` доступен admin/manager/storekeeper через общую матрицу ролей F04. Оператор заказов не монтирует страницу, её запросы, приёмку или детали. Таблица на широком экране и карточки на мобильном используют общий DataTable, Inter, SVG и CSS-токены. Список показывает номер, создание записи, фактическую приёмку, число исходных позиций (включая израсходованные партии), сотрудника и серверный статус `received`.

## Опубликованный контракт

`frontend/src/entities/supply/model/contracts.ts` проверяет SupplySummary и ListEnvelope из `backend/docs/openapi.yaml`. Поля `created_at` и `received_at` независимы, RFC3339 включает timezone и до девяти дробных разрядов. `items_count` — целое 1–100; meta списка — объект, текущий backend возвращает `{}`. RTK Query использует общий cookie/session transport. Неверная схема, дубли ID или несовпадение номера/размера страницы отклоняются до отображения. Frontend не меняет backend и не добавляет собственный статус поставки.

`GET /api/v1/supplies` принимает только `search`, `from`, `to`, `sort=-created_at`, `page`, `page_size`. Поиск по номеру буквальный и без учёта регистра; `%`, `_`, `\` не превращаются в шаблоны. Сортировку `created_at DESC, id DESC`, total после фильтров и до пагинации выполняет сервер. Размер страницы 1–100, default 50. Неизвестные URL-поля отбрасываются, небезопасные номера страниц нормализуются. Смена поиска/периода/размера страницы сбрасывает page. URL сохраняет фильтры при reload, Back/Forward и возврате после входа.

## Период и время ресторана

Форма React Hook Form/Zod принимает локальные дату и время в `session.settings.timezone`. Поля «Создана с (включительно)» и «Создана до (не включая)» задают `[from,to)` по `created_at`, а не `received_at`. Чтобы выбрать весь день 10 октября, укажите с `10.10 00:00` до `11.10 00:00`. Для Europe/Moscow запрос передаст `from=2026-10-09T21:00:00Z` и `to=2026-10-10T21:00:00Z`. Часовой пояс браузера не участвует. Односторонние и равные границы допустимы; равные дают пустую выборку.

Невозможные даты, введённые неоднозначные/отсутствующие DST-времена и обратный период дают связанную с полем ошибку. Некорректные from/to из URL показывают отдельное состояние и не запускают запрос. Сброс или исправление формы восстанавливает работу. Нативный datetime-local редактирует до миллисекунд; неизменённая граница из URL сохраняет исходные наносекунды и offset, включая уже однозначный API instant в повторяющийся час DST. Сравнение границ сохраняет все девять разрядов, BigInt используется только локально и не попадает в Redux/JSON.

## Состояния и обновление

Первичная загрузка, пустая история, отсутствие результатов, страница после конца и ошибка различаются. Ошибка первой загрузки не показывается как пустая история. При фоновом обновлении остаётся текущий список; после неудачи появляется явное предупреждение, что это последний успешный ответ и данные могут устареть. `currentData` никогда не подставляет результаты других фильтров. Серверный 403 скрывает даже закэшированные записи и сохраняет сессию; 401 обрабатывается общим session transport. Кнопки обновления/повтора, возврата к первой странице и сброса доступны с клавиатуры.

Ссылки в детали `/supplies/:id` и приёмку `/supplies/new` несут `returnTo` с разрешёнными фильтрами списка. `safeSupplyListUrl` ограничивает возврат путём `/supplies`, отбрасывает hash и чужие/секретные параметры. F07 реализует состав поставки с обратной ссылкой; F08 реализует приёмку с результатом и обратной ссылкой. Возврат монтирует список с `refetchOnMountOrArgChange: true`, поэтому он повторно запрашивает сервер даже при наличии cache.

F08 mutation инвалидирует `Supplies` после подтверждённого POST, в том числе после идемпотентного replay; `invalidateSupplies()` из `frontend/src/entities/supply/index.ts` остаётся доступен для явного обновления. Тег `Supplies` обновляет все активные страницы/фильтры; неактивные будут загружены при следующем входе. F06 тестирует этот механизм и возврат с изменившейся synthetic history, не заявляя реализованным POST.

## Проверки и интеграция

`./scripts/frontend-checks.sh` выполняет lint, TypeScript, Vitest и production build. `cd frontend && npm run test:browser` выполняет Chromium-сценарии; для установленного браузера можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/Applications/Chromium.app/Contents/MacOS/Chromium`.

MSW работает только при явном `VITE_ENABLE_MOCKS=true` в development/test. `supply-handlers.ts` использует опубликованную схему и literal search, точные границы, порядок и пагинацию. Synthetic history содержит разные created_at/received_at, записи на обеих границах, одинаковые created_at с разными UUID и наносекунды. `supplies-empty` показывает пустую историю; `supplies-received` добавляет тестовую сводку для проверки обновления. Общие slow/network-error/forbidden/server-error/invalid-schema проверяют транспорт. Неизвестные API по-прежнему возвращают явный mock 501; автоматического перехода с real API на fixtures нет.

Vitest проверяет контракт, URL, DST, наносекунды, серверную пагинацию, текущий cache при ошибке/403, роли, безопасный returnTo и инвалидирование. Браузер проверяет 360/390/1024/1440, клавиатуру, overflow, login return, reload/Back/Forward, фильтры, формы, loading/empty/error и обновление при возврате. Эти проверки не упражняют настоящий сервер. Реальные cookie/session/RBAC и supply reads S06 требуют отдельного прогона с отключёнными моками и тестовой серверной сессией. Согласование изолированного F03 auth-адаптера с текущим опубликованным auth-контрактом остаётся отдельным follow-up.


## Детали принятой поставки (F07)

`/supplies/:id` использует опубликованный `GET /supplies/{id}` без query-параметров. `SupplyDetail` расширяет сводку массивом `{product: ProductBrief, batch: Batch}` и обязательным `meta.server_time`. Общие DTO-схемы ProductBrief/Batch находятся в `src/shared/api/warehouse-contracts.ts`; inventory и supply используют их без импорта соседних entities. Ответ с несовпадающим id/количеством строк, дубликатами batch.id или несогласованными ссылками/единицами отклоняется до отображения.

Шапка показывает номер, фактический `received_at`, время создания записи `created_at`, сотрудника и число исходных строк. Таблица на широком экране и карточки до 1100 px показывают line_number, название продукта, ID партии, точное исходное количество, текущий остаток, фактический срок и серверный статус. Повторные продукты не объединяются; ключ — batch.id. Порядок строк сохраняется из серверного снимка (`line_number ASC, id ASC` по контракту). Количества переведены в опубликованный display_unit без Number/округления. Статус и срок не пересчитываются по браузерным часам или стандартному сроку продукта. Израсходованные партии с нулём и партии отключённых продуктов остаются в истории. Принятая поставка не имеет кнопок или endpoint редактирования/удаления.

Загрузка и повтор используют UI-kit; обновление сохраняет только последний снимок текущего id. Сетевой сбой показывает предупреждение об устаревших данных. Новый id использует currentData и не показывает другую поставку. Ресурсный 404 скрывает старый cache и показывает «Поставка не найдена» с возвратом к истории; неверный UUID показывает ошибку адреса без запроса. Серверный 403 скрывает детали и не очищает сессию. 401 остаётся ответственностью общего session transport. Переходы/вход/reload сохраняют безопасный returnTo списка из F06. При повторном входе детали обновляются; тег Supplies охватывает сводки и детали.

«На склад» передаёт search по названию и UI-only product_id/supply_id. Эти UUID допускаются в безопасном login-return URL, но никогда не отправляются как неизвестные параметры GET /inventory или GET /products/{id}/batches. Склад отображает отдельную панель точного выбранного продукта, прочитав ProductBrief из поставки. Поэтому история доступна даже при пустом складском поиске/нулевом остатке/отключённом продукте. Панель открывает status=all, отмечает партии выбранной поставки и использует опубликованные фильтры/FEFO/пагинацию F05. Остальные партии продукта доступны для сравнения; UI не выдаёт частичную страницу за отфильтрованную сервером поставку. Изменение фильтров склада сохраняет выбор; «Снять выбор поставки» или общий сброс его удаляет. Browser Back возвращает исходную деталь с фильтрами истории; «К истории поставок» восстанавливает список. Оператор заказов читает обычный склад, но даже подделанный product_id/supply_id не монтирует supply-панель и не вызывает GET /supplies.

MSW-детали используют тот же синтетический снимок партий, что и склад: 27 отдельных строк, 23 строки «Молоко», одна израсходованная партия, отключённый продукт, точные большие kg-количества и pcs. Общие сценарии loading/network-error/forbidden/invalid-schema дополнены supply-not-found. Vitest проверяет контракт, транспорт, строки, cache/404/403, восстановление и выбор склада; Chromium проверяет четыре ширины, клавиатуру, login/reload/Back, возврат фильтров и запрет supply reads оператору. Реальные S06 GET /supplies/{id}, cookie/session и RBAC требуют отдельного прогона с VITE_ENABLE_MOCKS=false. Моковый режим не доказывает интеграцию с сервером; production не содержит mock fallback. POST реализован в F08 ниже.

## Приёмка (F08)

`/supplies/new` теперь содержит React Hook Form/Zod с номером, фактической датой приёмки и 1–100 исходными строками. Активные продукты читаются через опубликованный `GET /products?is_active=true&sort=name&page_size=100`; каталог загружается постранично до полного результата, ошибки/пустой каталог не разрешают новую отправку. Одинаковые продукты допустимы в отдельных строках. Доступ сохраняет существующая матрица admin/manager/storekeeper.

Простой explicit-режим отправляет только `{number, received_at, items:[{product_id, quantity, expires_at}]}` из CreateSupplyRequest. Номер обрезается по краям; количество строго положительно, pcs — целое. g/kg/ml/l конвертируются точными shared-утилитами в строку базовых единиц numeric(14,3), без float/округления. Время вводится в settings.timezone, переводится в RFC3339; срок должен строго превышать приёмку. Текущую просрочку и актуальную активность продукта окончательно проверяет сервер. Производство/расчётный срок не отправляются.

Одна попытка получает `crypto.randomUUID()` в `Idempotency-Key`. Исходное тело и ключ фиксируются до POST и не изменяются. Изменение строк/порядка запрещено во время отправки. `422 error.details.fields` отображается по индексу исходного payload (`items[n].quantity/product_id/expires_at`, number, received_at) и фокусирует первое известное поле. Конфликт номера и определённый отказ сохраняют значения, разрешая корректировку и новый UUID. Автоматических повторов нет.

Сеть/таймаут/5xx/повреждённый успешный ответ/REQUEST_IN_PROGRESS/IDEMPOTENCY_CONFLICT/смена сессии сохраняют неопределённую попытку. Ответы 403/429 также сохраняют её: проверки доступа или лимита могут отклонить повтор до чтения сохранённого результата и не подтверждают исход первой отправки. UI запрещает редактирование и предлагает ручной повтор точного исходного запроса с тем же UUID. Повтор обходит повторную клиентскую валидацию по текущему каталогу, чтобы отключение продукта или изменение timezone не меняло уже отправленное тело. Минимальная серверная гарантия хранения — 24 часа; frontend прекращает повторы через 23 часа от начала попытки (или при переводе часов назад), сохраняет данные и предлагает выяснение результата через историю/ответственного сотрудника. Он не создаёт новый ключ для потенциально принятой поставки.

Несекретные значения и попытка проходят явную schema-allowlist и сохраняются у текущего owner в Redux и tab-local sessionStorage (`flagman.reception.v1`). Восстановление из storage происходит только после восстановления сессии, при совпадении user.id. Истечение сохраняет draft для повторного входа того же пользователя; logout или смена пользователя удаляют его. Токены, CSRF, cookie и auth-поля туда не попадают. При недоступном sessionStorage работает только память страницы; закрытие вкладки завершает tab-local хранение. Подтверждённый и согласованный SupplyDetail очищает draft. Перезагрузка после успеха показывает новую пустую форму; поставка доступна в истории.

Успех показывает серверный номер, даты, реальные ProductBrief/Batch, отдельные batch.id/line_number, исходные количества/сроки и переходы в детали/склад. Ответ проверяется против отправленных строк; количества сравниваются по точному значению (1000 и 1000.000 эквивалентны), даты — по моменту времени. Некорректный снимок не считается подтверждением. Инвалидируются Supplies, Inventory, Batches, Dashboard, Dishes, StopList, Recommendations. Последние четыре тега зарезервированы для соответствующих будущих read endpoints: они должны предоставлять эти теги. Принятая поставка остаётся неизменяемой.

MSW остаётся явным development/test режимом. Reception-сценарии: products-empty/error/slow; reception-slow/network/lost-response/validation/conflict/in-progress. Потерянный ответ моделируется после сохранения результата; повтор возвращает ту же поставку без добавления второй. Mock-only sessionStorage сохраняет синтетический результат между reload. История/детали/остатки/партии отражают синтетическую приёмку. Это проверка поведения frontend, а не реальной транзакции/дедупликации сервера. Production использует реальные запросы и не содержит fallback. Реальная S05/S07/S15 интеграция, cookie/session/CSRF/Origin/RBAC и согласование F03 auth-адаптера требуют отдельной проверки с моками выключенными.
