# Кладовая: flow разработки frontend по экранам

Рабочий бэклог frontend для хакатона: основные экраны, формы, администрирование, списания, аналитика и обновления данных. Основа — согласованная спецификация в корневом README и [Flow(Backend&Infra)](https://ru.yougile.com/team/0608bf797048/umirHack__dash__flagman/doc/UMI-13). Дизайн — существующий файл Figma и ресурсы проекта; этот план не утверждает, что все фреймы Figma просмотрены.

Результат frontend-стори принимается в браузере: пользователь видит экран, выполняет действие, получает понятный результат и может продолжить работу. Для каждого экрана есть задачи по интерфейсу, данным, действиям и состояниям. Desktop/Tablet/Mobile — варианты одного экрана, а не отдельные стори.

## Как устроен бэклог

| Уровень | Что это | Пример |
|---|---|---|
| Эпик | Группа связанных экранов | «Поставки и склад» |
| Стори | Экран или законченный сценарий пользователя | «Кладовщик принимает новую поставку» |
| Таска | Конкретная работа внутри стори | «Связать ошибки items[2].quantity с третьей строкой формы» |

Идентификаторы `F01–F31` относятся к frontend; `S01–S28` — к существующему backend-плану. Это позволяет ссылаться на зависимости без путаницы. Все стори имеют направление `[FE]`.

При переносе в dev: одна стори — одна родительская задача, пункты `Fxx-Txx` — её подзадачи. Исполнители заранее не назначаются. Группировку по эпикам можно хранить в описании и существующих стикерах. Этот документ сам по себе не создаёт карточки на dev.

## Что уже есть и что предстоит сделать

В frontend уже есть React + TypeScript + Vite, зависимости Redux Toolkit/RTK Query, React Hook Form/Zod и React Router, каркас FSD, алиас `@`, локальные шрифты, SVG-иконки и CSS-токены. `App` пока возвращает `null`. Переиспользуем существующие ресурсы; наличие зависимости или пустой директории не означает готовность функциональности.

На момент составления плана единственный предметно доступный HTTP-маршрут backend — healthcheck; бизнес-API ниже описывают целевую интеграцию. Пока соответствующая backend-стори не готова, экран можно разрабатывать на локальных моках согласованного контракта. Стори считается законченной после подключения и проверки реального API. Моковый ответ не должен скрытно подменять ошибку реального backend.

## Общие правила реализации

- Сохраняем FSD: `app → pages → widgets → features → entities → shared`. Страница собирает экран, feature реализует действие, entity содержит данные сущности, shared — общие компоненты и инфраструктуру. Новые слайсы создаём по мере появления кода; внешние импорты через `index.ts`.
- RTK Query хранит серверные данные; Redux — только общее клиентское состояние, например корзину и сессию без секретов. Состояние полей формы — React Hook Form; поисковые фильтры и страница списка — URL. Не копируем ответы API во второй Redux-слайс без причины.
- Все бизнес-запросы идут через `/api/v1`; nginx/Vite проксируют на backend того же origin. Cookie управляется браузером, CSRF-токен передаётся в изменяющих запросах. Права определяются через `/auth/me` и проверяются сервером.
- Количества остаются точными decimal-строками. Преобразование кг/л в g/ml выполняется без `parseFloat` и арифметики двоичных дробей. Для `numeric(14,3)` после перевода в базовую единицу допустимы максимум 11 цифр до точки и 3 после; `pcs` — целые, положительность зависит от поля.
- Даты вводятся и отображаются в `settings.timezone`, по умолчанию `Europe/Moscow`; в API отправляются RFC 3339 с часовым поясом. Часовой пояс устройства не подменяет ресторанный.
- Ошибка имеет вид `{error:{code,message,details},request_id}`. `422` привязывается к полям; `409` — к конкретному конфликту; `413` и `429` — к размеру запроса и частоте. Не показываем пользователю SQL, stack trace или сырой ответ прокси.
- До SSE опрашиваем разрешённые данные активного экрана раз в 10 секунд при видимой вкладке, обновляем на возврате фокуса/сети. После записи инвалидируем все связанные данные. Числа остатков и доступности берём у сервера; optimistic update для складского учёта не применяем.
- При неопределённом результате записи сохраняем неизменные payload и Idempotency-Key и сначала выясняем исход повтором той же попытки. Изменение формы или новый ключ не заменяют выяснение исхода: предыдущая операция могла уже сохраниться. После известного результата отдельное новое действие получает новый ключ.
- Формы сохраняют данные при ошибке. Локальный черновик привязан к пользователю; после истечения сессии доступен тому же пользователю, после явного выхода очищается и не раскрывается следующему вошедшему. Пароли/CSRF/session token в черновики не попадают.
- Каждому экрану нужны загрузка, пустое состояние, поиск без результатов, ошибка с повтором и сохранением последних данных. Формам дополнительно нужны отправка, ошибки полей, конфликт, успех и подтверждение ухода с изменениями.
- Эталонные ширины — 1440/1024/390 px; минимальная — 360 px. Для таблиц есть мобильные карточки с теми же данными. Нужны label, видимый фокус, клавиатура, управление фокусом диалогов, `aria-describedby` для ошибок и `aria-live` для уведомлений. Значение статуса передаётся текстом, а не только цветом.

## Порядок выполнения

| Шаг | Стори | Результат |
|---|---|---|
| 1 | F01 → F02 → F03 → F04 | Приложение, общие компоненты, вход и навигация по ролям |
| 2 | F05, F06 → F07/F08 | Можно принять поставку, увидеть её состав и партии на складе |
| 3 | F09, F10 → F11, F12 | Можно проверить и оформить заказ, увидеть списание и стоп-лист |
| 4 | F13/F14 → F15 | Рекомендации и сводка на главной странице |
| 5 | F16–F24 | Управление справочниками, пользователями, настройками и аудитом |
| 6 | F25 → F26 → F27/F28/F29 | Списания, история движений, аналитика и прогноз |
| 7 | F30 → F31 | Обновления через SSE и приёмка всей системы |

Первый сквозной результат: вход → новая поставка → склад → новый заказ → детали списания → обновлённый склад и стоп-лист. Обзор можно начать раньше на моках, но завершить после готовности `/dashboard`.

После общей основы независимые экраны можно делать параллельно. F16–F24 зависят от входа и соответствующих API, а не от завершения всех рекомендаций. F30 подключается к готовым экранам по мере появления SSE; его не нужно откладывать до последнего дня. F31 включает уже выполненные проверки каждой стори, а не становится первым моментом интеграции.

## Что считать готовой frontend-стори

1. Экран доступен по заявленному маршруту/действию и связан с реальным API, если интеграция входит в стори; моковая вёрстка отдельно помечена как промежуточный результат.
2. Выполнены её критерии приёмки, показаны необходимые загрузка/пустота/нет результатов/ошибка и состояния формы. Ошибка не стирает пользовательский ввод.
3. Права проверены на уровне навигации/действий, серверные `401/403` обработаны; запрещённые вложенные запросы не отправляются.
4. Значения точны, единицы/время соответствуют контракту; list total и пагинация не вычислены только по видимой странице.
5. После записи обновляются связанные разделы; повтор действия безопасен согласно контракту, устаревший ответ не заменяет свежие данные.
6. Экран работает на 360–1440 px, доступен с клавиатуры, содержит подписи и текстовые причины статусов.
7. Код использует существующие UI/API/FSD-модули, проходит предусмотренные lint/build и проверки поведения; изменения контракта отражены в документации вместе с backend.

## Как переносить в YouGile dev

Название карточки — заголовок `Fxx`. Описание — экран, результат, зависимости FE/BE, API и приёмка. Каждая строка `Fxx-Txx` становится подзадачей этой карточки. Исполнителей не назначать; существующий стикер frontend выбрать только из доступных, не создавать новый без необходимости. Нельзя считать код Fxx техническим id объекта YouGile: реальные id назначает трекер.

Эпики FE-E01–FE-E09 группируют работу, но не заменяют экранные стори. Не заводить отдельные стори «написать компонент», «подключить fetch» и «добавить Redux» для одного пользовательского результата. Крупная F10 разбита на семь конкретных шагов, её готовность требует всей цепочки корзина → check → submit → результат.

Админка и дополнительные экраны остаются в плане, даже если первый демонстрационный проход ограничен складом/поставками/заказами. Автосписание реализует backend worker S21; frontend даёт настройку, показывает движения и обновлённые остатки. Генератор событий S25 и мониторинг S26 используют готовые API/инструменты, отдельные пользовательские формы для них не добавляются без нового требования.
