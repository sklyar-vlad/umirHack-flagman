# Кладовая

Веб-интерфейс для управления ресторанным складом, разработанный в рамках хакатона «Флагман». Проект объединяет учет продуктов и партий, контроль сроков годности, оформление заказов и рекомендации по закупкам.

[Дизайн в Figma](https://www.figma.com/design/rP1JjraHWpqUFwm5c2bgJb) · [Описание проекта и контракт API](../README.md) · [Инфраструктура](../infrastructure/README.md)

## Текущее состояние

Подключены Redux store, типизированные hooks, React Router и общий RTK Query-клиент. На главной странице отображается стартовый экран; бизнес-разделы ниже описывают целевую функциональность и ещё не реализованы.

В режиме `npm run dev` доступна страница `/dev/api`: загрузка, ответ healthcheck, повтор запроса и безопасное описание ошибок. При фоновом сбое сохраняется последний успешный ответ. Страница и ссылка на неё исключены из production-сборки. Healthcheck проверяет только доступность HTTP-процесса, а не готовность БД и бизнес-операций.

## Функциональность проекта

| Раздел | Назначение |
|---|---|
| Склад | Общие остатки продуктов, партии, поиск и фильтрация по срокам годности |
| Поставки | Прием продуктов отдельными партиями и просмотр истории поступлений |
| Заказы | Проверка доступности ингредиентов и оформление заказов из нескольких блюд |
| Стоп-лист | Перечень блюд, недоступных из-за нехватки годных продуктов |
| Рекомендации | Расчет потребности в закупках и приоритет продажи блюд |
| Обзор | Основные показатели склада и уведомления о проблемных остатках |
| Администрирование | Управление продуктами, рецептурами, пользователями и настройками |

Основные сценарии: прием поставки, проверка состава заказа, списание ингредиентов по партиям и обновление доступности блюд. Просроченные продукты исключаются из годного остатка. При нехватке ингредиентов заказ не проводится, а интерфейс показывает причину отказа.

## Локальный запуск

Требования: Node.js 22.22 или новее, npm.

Команды выполняются из корня репозитория:

```sh
cd frontend
npm ci
npm run dev
```

Адрес сервера разработки выводится в терминале. Установка выполняется по `package-lock.json`.

### Доступные команды

| Команда | Действие |
|---|---|
| `npm run dev` | Запуск сервера разработки |
| `npm run build` | Проверка TypeScript и сборка в `dist/` |
| `npm run preview` | Локальный просмотр собранного приложения |
| `npm run lint` | Проверка кода ESLint |
| `npm run typecheck` | Проверка TypeScript без сборки |
| `npm run test` | Локальные тесты Vitest без реальных API-запросов |

Для просмотра production-сборки:

```sh
npm run build
npm run preview
```

Запуск приложения вместе с backend и PostgreSQL описан в [документации инфраструктуры](../infrastructure/README.md).

### Разработка с моками

MSW включается только в development и только при `VITE_ENABLE_MOCKS=true`. По умолчанию запросы направляются в реальный backend. Для включения создайте `frontend/.env.local` со значениями:

```dotenv
VITE_ENABLE_MOCKS=true
VITE_MOCK_SCENARIO=success
```

После изменения файла перезапустите `npm run dev`. На всех страницах появится панель «Моковый режим» со сценариями healthcheck. Перехват запускается до рендера React и первого API-запроса; ошибка запуска показывает отдельный экран, без автоматического обращения к backend.

Сценарии: `success`, `slow` (2 секунды), `network-error`, `unauthorized` (401), `forbidden` (403), `conflict` (409), `validation-error` (422), `rate-limit` (429), `server-error` (500), `bad-gateway` (502/HTML), `invalid-json`, `invalid-schema`. Панель меняет сценарий и обновляет активную подписку healthcheck. При обновлении страницы восстанавливается сценарий из env; во время запроса переключатель отключён.

Сейчас замокан только `GET /api/v1/healthcheck`. Ошибки на этом публичном маршруте намеренно форсируются для проверки интерфейса и транспорта. Остальные `/api/v1`-маршруты, включая операции записи, возвращают `501 MOCK_NOT_IMPLEMENTED` и не направляются в backend. Статические ресурсы и HMR не перехватываются. Моки авторизации, списков и бизнес-операций добавляются вместе с реализацией соответствующих экранов.

Чтобы вернуться к реальному API, задайте `VITE_ENABLE_MOCKS=false` и перезапустите Vite. В production worker не запускается даже при включённом флаге, а код панели и обработчиков исключается из сборки.

Файл `public/mockServiceWorker.js` генерируется MSW и хранится в репозитории. При обновлении версии MSW его следует обновить командой `npx msw init public --save`; вручную файл не редактируется. Исходные настройки без секретов находятся в `.env.example`, `.env.local` игнорируется Git.

## Архитектура

Проект организован по Feature-Sliced Design. Зависимости направлены от верхних слоев к нижним:

```text
app → pages → widgets → features → entities → shared
```

```text
src/
├── main.tsx          # точка входа
├── app/              # корень приложения, провайдеры, маршруты, store и стили
├── pages/            # страницы приложения и админки
├── widgets/          # крупные блоки интерфейса и навигация
├── features/         # действия пользователя
├── entities/         # бизнес-сущности
└── shared/           # UI-kit, API-клиент, конфигурация и общие ресурсы
```

Бизнес-сущности: продукт, партия, поставка, заказ, блюдо и пользователь. Основные действия выделены в слайсы `create-supply`, `create-order`, `check-order-availability`, `filter-stock` и слайсы управления справочниками.

Внутри слайсов используются сегменты `ui`, `model` и `api`. Внешние импорты проходят через публичный API слайса — `index.ts`. Алиас `@` указывает на `src` и настроен в TypeScript и Vite.

Часть структуры пока представлена пустыми директориями. Git сохраняет их после добавления файлов.

## Интеграция с API

Префикс API — `/api/v1`. Методы, форматы запросов и ошибок описаны в [контракте команды](../README.md#эндпоинты). Фактически реализованные методы определяются кодом backend; контракт описывает целевую функциональность.

Основные договоренности:

- Количества передаются decimal-строками; единицы измерения — `g`, `ml`, `pcs`.
- Даты передаются с часовым поясом. Ответы используют UTC, интерфейс — московское время.
- Доступность всего заказа и списание по FEFO проверяются на сервере. Проверка заказа не резервирует остатки.
- Создание поставки и заказа предусматривает `Idempotency-Key` для защиты от повторного проведения операции.
- Ошибки валидации полей и конфликты доступности отображаются без потери введенных данных.

В Docker nginx проксирует `/api/` на backend. При локальном запуске Vite направляет запросы `/api` через Traefik на `http://api.flagman.localhost`, сохраняя исходный путь. Backend и Traefik должны быть запущены через инфраструктуру проекта.

Frontend обращается к относительным адресам, например `/api/v1/healthcheck`: один путь используется и в разработке, и в Docker. Конфигурация dev-прокси находится в `vite.config.ts`; дополнительные переменные окружения для него не требуются.

Единый `baseApi` находится в `src/shared/api`; запросы сущностей добавляются через `baseApi.injectEndpoints`. Его reducer и middleware подключены в `src/app/store`. Cookie отправляются с `credentials: 'include'`; ошибки сети, таймаута, JSON и HTML-ответов прокси приводятся к `ApiError`, сохраняя `request_id`, ошибки полей и исходный `Retry-After`. Изменяющие запросы автоматически не повторяются.

Транспорт получает CSRF через `thunk.extraArgument`, поэтому `shared/api` не зависит от store приложения. `setCsrfToken` в `app/store` обновляет токен только в памяти; заголовок `X-CSRF-Token` добавляется для методов записи. Вход, восстановление сессии и обновление токена пока не реализованы. Обработчики focus/online подключены с очисткой при размонтировании провайдера.

### Точные количества и ресторанное время (F01)

Общие преобразования доступны через публичные API `@/shared/lib/quantity` и `@/shared/lib/restaurant-time`. Они не зависят от store или бизнес-сущностей. Тесты запускаются `npm run test`; полный gate из корня — `./scripts/frontend-checks.sh`.

`parseQuantity` и `serializeQuantity` переводят API-строку в BigInt тысячных долей базовой единицы и обратно, сохраняя `null`. Ввод ограничен `numeric(14,3)`: максимум `99999999999.999`, до трёх дробных знаков, без знаков, пробелов и экспоненты. BigInt нужен только для вычислений: в JSON, RTK Query и Redux передавайте строки.

`quantityFromInput('1,000001', 'g', 'kg')` возвращает `'1000.001'`. Форма допускает точку или запятую и внешние пробелы; кг/л допускают шесть дробных знаков, г/мл — три. Ничего не округляется; граница проверяется после перевода в базовую единицу. По умолчанию требуется положительное количество; для целевого запаса используйте `{ allowZero: true }`. Пустой необязательный целевой запас преобразуйте в `null` в схеме формы, отдельно от нуля.

`quantityToInput` возвращает точную строку без единицы, `formatQuantity` — подпись для UI (`'1,000001 кг'`, для `null` — `'—'`). Чтение складских агрегатов допускает превышение предела отдельной партии. Совместимы только g/g или g/kg, ml/ml или ml/l и pcs/pcs; штуки должны быть целыми. Для знаковых движений используйте отдельные `parseMovementQuantity`, `serializeMovementQuantity`, `formatMovementQuantity`: поступление отображается с `+`, списание с `-`. Ошибки имеют тип `QuantityError` и стабильный `code` для привязки к валидации формы.

`restaurantDateTimeToInput` переводит RFC3339 с обязательным смещением в строку для `datetime-local`; `restaurantDateTimeFromInput` переводит обратно в UTC с `Z`. Передавайте `settings.timezone`, по умолчанию используется `Europe/Moscow`; часовой пояс браузера не участвует. `null` сохраняется, пустой необязательный ввод становится `null`. Строковые преобразования сохраняют дробные секунды до девяти знаков; `parseApiDateTime` возвращает обычный Date с точностью до миллисекунд. `formatRestaurantDateTime` выводит дату и время до секунд, для `null` — `'—'`.

Невозможные даты, неизвестные пояса IANA и локальное время в пропущенном или повторяющемся часе DST вызывают `RestaurantTimeError` (`invalid_datetime`, `invalid_timezone`, `nonexistent_time`, `ambiguous_time`). Форма должна показать ошибку и предложить выбрать однозначное время; автоматический сдвиг даты не применяется. При редактировании существующего момента в повторяющемся часе сохраните исходную API-строку, если пользователь не изменял поле.
