# Флагман

Делаем приложение для ресторана: какие продукты есть на складе, что скоро испортится, какие блюда можно приготовить и что лучше продавать в первую очередь.

Бэк — Go + PostgreSQL. Фронт — React + TypeScript. Это предлагаемый план реализации кейса, стек можно поменять.

## Что должно работать

- Принимаем поставку и добавляем продукты на склад отдельными партиями.
- Показываем общий остаток продукта и остатки каждой партии.
- Отмечаем продукты, которые скоро испортятся или уже просрочены.
- Оформляем заказ из нескольких блюд и списываем ингредиенты по рецептам.
- Если ингредиентов не хватает, не оформляем заказ и объясняем почему.
- Автоматически отправляем недоступные блюда в стоп-лист и возвращаем их после пополнения.
- Подсказываем, какие продукты нужно докупить.
- Показываем горячие предложения: блюда, которые помогут использовать продукты с истекающим сроком.

## Что делаем на фронте

| Страница | Что на ней | Какие запросы нужны |
|---|---|---|
| Склад | Продукты, годный остаток, просрочка, ближайший срок. Поиск и фильтры | `GET /inventory` |
| Партии продукта | Из какой поставки партия, сколько осталось, когда испортится | `GET /products/{id}/batches` |
| Поставки | История поставок, просмотр состава, кнопка добавления | `GET /supplies`, `GET /supplies/{id}`, `POST /supplies` |
| Меню | Блюда, состав на порцию, сколько порций доступно | `GET /dishes` |
| Стоп-лист | Недоступные блюда и каких ингредиентов не хватает | `GET /stop-list` |
| Заказы | Выбор блюд и порций, проверка корзины, оформление, история | `POST /orders/check`, `POST /orders`, `GET /orders`, `GET /orders/{id}` |
| Рекомендации | Что докупить и какие блюда продавать в первую очередь | `GET /procurement-recommendations`, `GET /hot-offers` |
| Обзор, если успеем | Счетчики проблемных партий и блюд в стоп-листе | `GET /dashboard` |

Не обязательно делать восемь отдельных страниц: партии можно открыть в модалке со склада, стоп-лист — вкладкой меню, рекомендации — двумя блоками на одной странице.

**Добавление поставки:** номер и дата приема. В каждой строке выбираем продукт, вводим количество, дату производства и срок хранения в часах. Единица подтягивается из продукта. Можно добавить несколько строк одного продукта с разными сроками.

**Создание заказа:** выбираем блюда, задаем число порций. Бэк проверяет всю корзину. Если не хватает продуктов, показываем конкретный дефицит. После успешного оформления обновляем склад, меню и рекомендации.

**Отображение сроков:** «Годен», «Истекает», «Просрочен», «Израсходован». Для нашего MVP «Истекает» означает, что осталось не больше 24 часов. Это выбранный нами порог, его можно изменить.

При загрузке показываем индикатор, при ошибке — сообщение и повтор. Форму при ошибке не очищаем. На время отправки отключаем кнопку. Данные обновляем после действий и раз в 10 секунд на активной странице. Расчеты доступности делает бэк.

## Что хранит бэк

| Сущность | Что хранит |
|---|---|
| Продукт | ID, название, единицу измерения, стандартный срок хранения, целевой запас |
| Поставка | ID, уникальный номер, дату приема, дату создания |
| Партия | Продукт, поставку, исходное количество, остаток, дату производства, срок хранения, дату окончания срока |
| Блюдо | ID, название |
| Рецепт | Блюдо, ингредиент, количество ингредиента на одну порцию |
| Заказ | ID, дату, блюда и число порций |
| Движение | Из какой партии сколько поступило или списалось, когда и по какой причине |

Продукт и партия — разные вещи. Например, «Томаты» — один продукт, но вчерашние 300 г и сегодняшние 500 г — две партии с разными сроками.

Продукты и рецепты для начала загружаем заранее через seed — скрипт заполнения БД. Отдельный редактор справочников можно добавить позже.

## Эндпоинты

Все пути ниже начинаются с `/api/v1`. Ответы — JSON.

| Метод и путь | Что делает и возвращает |
|---|---|
| `GET /products` | Продукты для выбора в форме: ID, название, единица, стандартный срок, целевой запас |
| `GET /inventory` | По каждому продукту: годный остаток, истекающее количество, просроченное количество, ближайший срок |
| `GET /products/{id}/batches` | Партии продукта: поставка, исходное количество, остаток, даты, статус |
| `GET /supplies` | История поставок: ID, номер, даты, число строк |
| `GET /supplies/{id}` | Одна поставка со всеми ее партиями |
| `POST /supplies` | Создает поставку, партии и движения поступления. Возвращает созданную поставку |
| `GET /dishes` | Блюда с рецептами, доступностью, числом доступных порций и причинами недоступности |
| `GET /stop-list` | Только недоступные блюда в том же формате |
| `POST /orders/check` | Проверяет корзину без списания. Возвращает `can_create` и список дефицитов |
| `POST /orders` | Повторно проверяет корзину, создает заказ и списывает продукты. Возвращает заказ и использованные партии |
| `GET /orders` | История успешных заказов |
| `GET /orders/{id}` | Блюда заказа и какие количества из каких партий списались |
| `GET /procurement-recommendations` | Продукты для закупки: остаток, целевой запас, сколько докупить |
| `GET /hot-offers` | Доступные блюда по приоритету продажи с объяснением и проблемными партиями |
| `GET /dashboard` | Число истекающих партий, просроченных партий и блюд в стоп-листе |

Поиск продуктов: `?search=томат`. Фильтр склада: `?filter=expiring`, `expired` или `deficit`; без фильтра — все продукты. Списки возвращают `{ "items": [...], "total": 10 }`. Пагинация: `?page=1&page_size=50`, максимум 100 на страницу.

### Пример поставки

`POST /api/v1/supplies`

```json
{
  "number": "S-101",
  "received_at": "2026-10-09T12:00:00Z",
  "items": [
    {
      "product_id": "uuid-томатов",
      "quantity": "1000.000",
      "produced_at": "2026-10-09T06:00:00Z",
      "shelf_life_hours": 24
    }
  ]
}
```

ID здесь для наглядности: в приложении подставляем настоящий UUID из справочника. Даты тоже пример; в форме используются реальные даты.

Бэк считает `expires_at = produced_at + shelf_life_hours`. В примере томаты годны до 10 октября 06:00 UTC. Нельзя принять уже просроченную партию, дату производства позже приема или прием из будущего. Количество должно быть больше нуля. Если одна строка неправильная, не сохраняем всю поставку.

### Пример заказа

Для `POST /orders/check` и `POST /orders` тело одинаковое:

```json
{
  "items": [
    { "dish_id": "uuid-салата", "portions": 2 },
    { "dish_id": "uuid-пасты", "portions": 1 }
  ]
}
```

Пример ответа проверки:

```json
{
  "can_create": false,
  "shortages": [
    {
      "product_id": "uuid-томатов",
      "product_name": "Томаты",
      "unit": "g",
      "required_quantity": "400.000",
      "available_quantity": "300.000",
      "missing_quantity": "100.000"
    }
  ]
}
```

Если хватает, `can_create: true`, а `shortages: []`. Проверка ничего не резервирует: при оформлении бэк проверяет заново.

### Пример блюда в меню

```json
{
  "id": "uuid-салата",
  "name": "Салат",
  "recipe": [
    {
      "product_id": "uuid-томатов",
      "product_name": "Томаты",
      "unit": "g",
      "quantity_per_portion": "200.000"
    }
  ],
  "is_available": true,
  "available_portions": "4",
  "shortages": []
}
```

Это короткий пример рецепта из одного ингредиента. В реальном блюде проверяем каждый ингредиент.

## Как работает основная логика

### Списание по партиям

Используем FEFO: сначала расходуем партию, которая раньше испортится.

Например, есть 300 г томатов до завтра и 500 г до послезавтра. Заказ требует 400 г. Списываем 300 г из первой партии и 100 г из второй. Во второй остается 400 г.

Просроченные партии вообще не участвуют. Если времени годности осталось ровно ноль — партия уже просрочена.

### Проверка всего заказа

Складываем потребность всех блюд по каждому ингредиенту. Если салат требует 200 г томатов, а паста еще 200 г, нужно 400 г на весь заказ.

При нехватке хотя бы одного ингредиента не создаем заказ и ничего не списываем. Создание заказа и все списания выполняем в одной транзакции. На время проведения блокируем затронутые продукты в одинаковом порядке по ID, чтобы два параллельных заказа не потратили один остаток.

### Стоп-лист

Для каждого ингредиента делим годный остаток на расход одной порции и округляем вниз. Минимальное число по всем ингредиентам — сколько порций блюда доступно.

Если получилось 0, блюдо в стоп-листе. После поставки или истечения срока пересчитываем при следующем запросе. Доступные порции разных блюд нельзя складывать: у них могут быть общие ингредиенты.

### Что докупить

У продукта задаем целевой запас. Нужно докупить `max(0, целевой запас - годный остаток)`.

Например, хотим держать 2000 г томатов, осталось 700 г — рекомендуем 1300 г. Если цель не задана, рекомендацию не выводим. Это простой расчет до целевого запаса, без прогноза спроса.

### Горячие предложения

Берем только доступные блюда. Для каждого смотрим, какие истекающие партии реально будут использованы по FEFO при приготовлении одной порции.

Чем ближе срок и чем большую долю такой партии использует порция, тем выше приоритет. Простая формула:

`приоритет = 100 × (1 - оставшиеся часы / 24) × (расход из партии / остаток партии)`.

Если затрагиваются несколько истекающих партий, берем максимальный результат. Сортируем по приоритету, при равенстве — по ближайшему сроку. Партии с остатком срока больше 24 часов и просрочку не рассматриваем.

В ответе нужны название блюда, приоритет, доступные порции и понятная причина: «Томаты из S-101 испортятся через 6 часов; одна порция использует 150 г из этой партии». Предложения рассчитываются отдельно и не резервируют общие ингредиенты.

## Несколько договоренностей между фронтом и бэком

- Единицы: `g`, `ml`, `pcs`. Для продукта одна фиксированная единица. Граммы и миллилитры могут быть дробными, штуки — целые.
- Количества передаем строками, например `"150.000"`, чтобы точно считать дроби. Бэк хранит decimal, без `float64`. Число порций в заказе — целое от 1 до 1000; вычисленный предел доступных порций возвращаем строкой.
- Даты передаем с часовым поясом, бэк отвечает UTC. Фронт показывает московское время.
- Успешное создание — `201`. Проверка корзины — `200`, даже если ингредиентов не хватает. Недостаток при оформлении — `409`, неправильные поля — `422`, отсутствие ресурса — `404`.
- Ошибка имеет вид `{ "error": { "code": "...", "message": "...", "details": {} } }`. Для нехватки `details.shortages` содержит такой же список, как проверка корзины.
- Для создания поставки и заказа фронт отправляет `Idempotency-Key` — случайный UUID попытки. При сетевом повторе оставляет тот же ключ и тело. Бэк возвращает прежний результат и не проводит действие повторно. Для измененного тела или новой попытки после отказа — новый ключ.

## В каком порядке делать

1. Подготовить БД, продукты и рецепты для демо.
2. Сделать поставки, склад и партии.
3. Сделать проверку заказа и списание по FEFO.
4. Подключить меню и автоматический стоп-лист.
5. Добавить предупреждения по срокам и рекомендации закупки.
6. Сделать горячие предложения с объяснением.
7. Если остается время — обзор, автосписание просрочки, аналитику и SSE вместо опроса раз в 10 секунд.

Пока не берем оплату, отмену заказов, несколько ресторанов и большой редактор справочников. Для первого демо достаточно одного склада и заранее заведенных блюд.

## Что показать на защите

Принять поставку → увидеть партии → оформить заказ → показать, что первой списалась партия с ближайшим сроком → исчерпать ингредиент и увидеть стоп-лист → показать отказ без частичного списания → пополнить продукт и вернуть блюдо → показать горячее предложение.

Отдельно проверить: просрочка не идет в заказ; два параллельных заказа не делают остаток отрицательным; повтор одного запроса не создает второй заказ. Демодаты строить относительно текущего времени, чтобы предложения не превратились в просрочку до защиты.
