# Проверка сценария перед защитой

```sh
task backend:demo
```

Нужны локальный Docker daemon через Unix socket, Compose, Go из `go.mod`,
Python 3 и Goose 3.27.1 (установка описана в [CI.md](CI.md)). Команда не читает
dotenv приложения, не подключается к его БД и не принимает адрес VPS.
Создаётся уникальный Compose project с PostgreSQL 18 на tmpfs и случайными
loopback-портами. Настоящие forward-миграции применяются Goose; штатный seeder
создаёт пользователей четырёх ролей с одноразовым случайным паролем. Единственная
дополнительная начальная SQL-запись — singleton настроек ресторана, у которого
нет create API. Каталог и склад изначально пустые.

Клиент создаёт категорию, продукт и два блюда через обычный admin API, принимает
200 g, проверяет партию и одну порцию, проводит заказ, сверяет сохранённую историю
и точный остаток 100 g. Второй заказ исчерпывает общий ингредиент: оба блюда
попадают в стоп-лист, закупка рекомендует 500 g. Поставка 200 g снимает стоп-лист,
закупка пересчитывается в 300 g, свежая истекающая партия даёт hot offers.
Все изменения склада идут через обычные `/supplies` и `/orders` с UUID-ключами.
Клиент соблюдает лимит API и проверяет logout.

Для локальной проверки отдельного этапа:

```sh
bash scripts/backend-ci.sh demo basic
python3 -m unittest discover -s scripts -p 'test_demo_backend.py' -v
```

Этап `bash scripts/backend-ci.sh demo admin` повторяет базовый сценарий, меняет
имя блюда и рецепт со 100 на 150 g. Старая версия получает `RECIPE_CHANGED`,
исторический заказ сохраняет все прежние JSON-поля, новый использует 150 g
и новую версию. Изменение порога 24 → 1 → 24 часа пересчитывает hot offers.
Создание пользователя, смена `order_operator` → `storekeeper` и деактивация
проверяют права и немедленный отзыв старых сессий. Admin видит before/after
аудит рецепта и записи пользователя; менеджер получает 403 на audit-log.

Этап `bash scripts/backend-ci.sh demo operations` добавляет:

- Ручное списание 40 g годной партии, истечение отдельной партии 50 g при
  выключенном воркере, ручное списание 10 g истёкшего остатка, включение воркера
  и автоматическое списание 40 g за минуту. История сохраняет системного автора
  `null`; отчёт раздельно показывает 50 g ручных и 40 g автоматических потерь.
- Реальный отказ `INSUFFICIENT_STOCK`, отчёт по дефицитам и прогноз с историей,
  явными допущениями и confidence `low`. Проверки доступа для всех четырёх ролей.
- SSE с возрастающими ID, безопасными полями, ограничениями тем для ролей,
  точным replay одного события после reconnect. Для проверки `resync.required`
  скрипт ускоряет только возраст публикации первой записи outbox в своей
  одноразовой БД на 25 часов; штатный dispatcher сам выполняет retention.
  Это тестовая подготовка метаданных, бизнес-таблицы не исправляются.
- Настоящий `cmd/demo-events` создаёт ровно две поставки через API, с явными
  `ENV=demo`, адресом, Origin, подтверждением и закреплённым ID блюда.
- Prometheus читает `/metrics` через внешний файл bearer-секрета и не имеет
  published-порта. Сам `/metrics` без/с неверным токеном возвращает 401.
  Grafana публикуется только на случайном loopback-порту, без anonymous/signup,
  с одноразовым внешним паролем. Проверяются provisioning дашборда, реальная SQL
  выборка склада через SELECT-only роль, запрет чтения `users` и scrape `up=1`
  через авторизованный datasource proxy. Пароль datasource не попадает в ответ.

Временные monitoring-контейнеры используют существующие versioned dashboards,
provisioning и роль; настройки production не меняются. Автосписание выключается
после проверки. Cookies и токены хранятся только в памяти клиента, monitoring
секреты — только в приватных файлах внешнего временного каталога.

Полный `task backend:demo` завершает проверку конкурентным сценарием. Два блюда
делят единственный `pcs`: независимые check проходят, объединённая корзина
показывает ровно один недостающий `pcs` и не создаёт попыток. Два запроса с разными
ключами, отправленные параллельно из отдельных сессий, дают один заказ и один
сохранённый отказ. Повтор каждого ключа возвращает тот же ответ и не добавляет
заказ/попытку; изменение тела даёт `IDEMPOTENCY_CONFLICT`. Остаток равен нулю,
сумма receipt/consumption движений точно согласуется с ним.

После этого перезапускается только принадлежащий сценарию backend: старый поток
закрывается, новый случайный loopback-порт читается из того же Compose project.
Cookie-сессии, старый заказ, успешный/отказной replay и SSE по Last-Event-ID
сохраняются. Новая поставка после reconnect получает больший cursor.
Проверка `TestOpenAPICoversRegisteredRoutes` сопоставляет каждую описанную операцию
с регистрацией маршрута, implementation status и уникальным operationId;
внутренний `/metrics` явно имеет server `/`, остальные — `/api/v1`.

Каждое расхождение статуса, точного количества или исторического факта завершает
команду с ненулевым кодом. Консоль показывает только название этапа и безопасную
ошибку; пароли, cookies, CSRF и тела login не печатаются. Секреты находятся в
приватном временном каталоге вне репозитория. EXIT/INT/TERM удаляют только
принадлежащие этому запуску контейнеры, сеть, образы и временные файлы.
Повтор команды создаёт новое окружение; исправлять БД вручную не требуется.

Это воспроизводимая проверка backend API. Реальный VPS rollout, сертификат
конечного домена и hosted CI выполняет владелец по [HTTPS.md](../infrastructure/HTTPS.md).
