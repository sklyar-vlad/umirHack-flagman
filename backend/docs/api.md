# Общие правила API

Основной предметный контракт описан в [README](../../README.md#rest-api). Базовый путь — `/api/v1`.

В проекте реализованы общие DTO и функции разбора параметров из S02-T01/S02-T02. Сейчас зарегистрирован только `GET /api/v1/healthcheck`; приведённые ниже бизнес-списки будут реализованы в соответствующих стори. Их handlers должны явно вызывать функции из `internal/validations`: регистрация пакета сама проверки не подключает.

## Ответ со списком

Структура: `dto.ListResponse[T]`, где `T` — тип одного элемента.

| Поле | Значение |
|---|---|
| `items` | Элементы текущей страницы; пустой список — `[]` |
| `total` | Количество записей после всех фильтров, до пагинации |
| `page` | Номер возвращённой страницы, начиная с 1 |
| `page_size` | Размер страницы, по умолчанию 50, максимум 100 |
| `meta` | Дополнительные сведения о выборке; без них — `{}` |

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 50,
  "meta": {}
}
```

Для ответов с расчётами `meta.server_time` задаёт момент расчёта в UTC. В `meta` также может передаваться `request_id`. Область расчёта каждого агрегата в `meta` должна быть описана в контракте конкретного эндпоинта.

Handler должен инициализировать пустые срезы и maps: нулевые значения этих полей сериализуются как `null`, а DTO сама не заменяет их на `[]` и `{}`. Одиночный ресурс возвращается напрямую.

## Ошибки

Внутренняя ошибка валидации: `validations.FieldError{Field, Message}`. Она содержит путь поля, например `page` или `items[0].quantity`, и объяснение ошибки. Функции разбора возвращают первую найденную ошибку; HTTP-ответ формирует handler.

### Текущая структура ответа

`dto.ErrorResponse` сейчас содержит поля непосредственно в корне JSON:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Некорректные параметры запроса",
  "details": {
    "page": "Ожидается целое число больше нуля"
  },
  "request_id": "req-123"
}
```

| Поле | Значение |
|---|---|
| `code` | Стабильный машинный код ошибки |
| `message` | Описание для пользователя |
| `details` | Дополнительные сведения; без них — `{}` |
| `request_id` | ID текущего HTTP-запроса, совпадающий с ID в логах |

### Согласование с README

README предусматривает вложенный объект `error` и список ошибок полей в `error.details.fields`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные параметры запроса",
    "details": {
      "fields": [
        {
          "path": "page",
          "code": "invalid_value",
          "message": "Ожидается целое число больше нуля"
        }
      ]
    }
  },
  "request_id": "req-123"
}
```

Это расхождение нужно устранить при согласовании DTO и общего преобразования ошибок в S02-T01/S02-T03. Описанный выше плоский формат отражает текущую структуру кода и не заменяет целевой контракт README. Код поля `invalid_value` в примере иллюстративный; перечень кодов полей определяется при реализации преобразования ошибок.

### HTTP-статусы

| Ситуация | Статус |
|---|---:|
| Невалидный JSON | 400 |
| Неверные значения полей, query-параметров, фильтров или сортировки (`VALIDATION_ERROR`) | 422 |
| Ресурс не найден (`NOT_FOUND`) | 404 |
| Внутренний сбой (`INTERNAL_ERROR`) | 500 |

Полный перечень статусов приведён в README. Внутренние SQL-ошибки записываются в лог и не раскрываются клиенту. Request ID, логирование и единое преобразование ошибок подключаются в S02-T03; сейчас отдельного middleware для request ID нет.

## Общий разбор параметров

| Функция | Назначение |
|---|---|
| `ValidateQuery(query, allowed...)` | Проверка разрешённых названий параметров и запрет повторов |
| `ParsePagination(query)` | Получение проверенных `dto.Pagination` |
| `ParseSort(query, defaultValue, allowed...)` | Получение проверенной `dto.Sort` |
| `ParseEnum(query, field, defaultValue, allowed...)` | Проверка значения из заданного списка |
| `ParseUUID(field, raw)` | Разбор идентификатора в `uuid.UUID` |
| `ParseDateTime(field, raw)` | Разбор временной отметки в `time.Time` с приведением к UTC |
| `ParseQuantity(field, raw)` | Разбор неотрицательного количества в `int64` в тысячных долях |

`ValidateQuery` проверяет названия и число значений. Тип и содержимое каждого параметра проверяются отдельным разбором. Сначала handler проверяет ошибку, затем использует возвращённый результат.

Списки допустимых параметров, сортировок и значений фильтров передаются конкретным handler. Значение по умолчанию для `ParseSort`/`ParseEnum` должно входить в разрешённый список.

### Пагинация

| Параметр | При отсутствии | Ограничение |
|---|---:|---|
| `page` | 1 | Целое число больше нуля |
| `page_size` | 50 | Целое число от 1 до 100 |

Неверные значения не заменяются значениями по умолчанию. `page=`, `page=abc`, `page=0`, `page_size=101` и повторные параметры отклоняются.

Результат разбора — `dto.Pagination{Page, PageSize}`. Ограничение выборки и безопасный расчёт смещения выполняются при реализации репозитория.

### UUID

Принимается строка из 36 символов в формате `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`; допускаются заглавные и строчные шестнадцатеричные символы. Запись без дефисов, пробелы и пустая строка отклоняются.

Результат — `github.com/google/uuid.UUID`. Парсер проверяет формат; существование сущности проверяется отдельно. Парсер не ограничивает версию UUID и не запрещает нулевой UUID.

### Дата и время

Разбор выполняется через `time.Parse(time.RFC3339Nano, raw)`. Требуется временная отметка с часовым смещением или `Z`; дробные секунды поддерживаются. Результат приводится к UTC.

```text
2026-10-10T15:30:00+03:00 -> 2026-10-10T12:30:00Z
2026-10-10T12:30:00.123Z  -> допустимо
2026-10-10T15:30:00      -> ошибка: отсутствует timezone
2026-02-30T12:30:00Z     -> ошибка: несуществующая дата
```

Необязательный временной фильтр разбирается только при наличии параметра. Временные ограничения предметной операции и проверка порядка границ выполняются отдельно. Для интервала `from` включительно, `to` исключительно; если обе границы переданы, `from` не должен быть позже `to`.

В URL знак `+` в часовом смещении должен быть закодирован как `%2B`; удобно формировать query через `url.Values.Encode()`. Можно использовать UTC с `Z`.

### Точные количества

В JSON количество передаётся строкой, например `"12.375"`. Текущий парсер принимает запись по шаблону `^\d{1,11}(\.\d{1,3})?$`:

- От 1 до 11 цифр до точки; ведущие нули также учитываются при проверке длины.
- От 1 до 3 цифр после точки, если точка присутствует.
- Только неотрицательные значения, включая ноль.
- Без пробелов, знака `+`, запятой и экспоненциальной записи.
- Лишние дробные знаки отклоняются без округления.

Ограничения соответствуют диапазону неотрицательных значений `numeric(14,3)`: максимум `99999999999.999`. Входной JSON-тип строки обеспечивается DTO конкретного запроса; `ParseQuantity` получает уже строку.

Результат — целое число в тысячных долях:

| Вход | Результат |
|---|---:|
| `"12"` | 12000 |
| `"12.5"` | 12500 |
| `"12.375"` | 12375 |
| `"0.001"` | 1 |
| `"0"` | 0 |

Преобразование через `float64` не используется. Перед записью в `numeric(14,3)` и выдачей JSON необходимо учитывать масштаб 1000: внутреннее значение 12375 означает `"12.375"`. Общая функция обратного форматирования пока не добавлена.

Положительность количества для приёмки/списания проверяется отдельно. Для единицы `pcs` количество должно быть целым: `quantity % 1000 == 0`. Знаковые изменения остатков (`delta_quantity`) требуют отдельного представления/форматирования; `ParseQuantity` предназначен для неотрицательных входных количеств.

## Фильтры и сортировки коллекций

Во всех перечисленных ниже коллекциях допустимы `page` и `page_size`. В таблице перечислены дополнительные фильтры; `sort` разрешён только там, где задан его допустимый список.

| Эндпоинт после `/api/v1` | Дополнительные фильтры | Допустимый `sort` |
|---|---|---|
| `/products` | `search`, `category_id`, `is_active` | `name` |
| `/inventory` | `search`, `category_id`, `filter` | `name`, `nearest_expires_at` |
| `/products/{id}/batches` | `status`, `supply_id` | `expires_at`, `-created_at` |
| `/supplies` | `search`, `from`, `to` | `-created_at` |
| `/dishes` | `search`, `is_active`, `availability` | `name` |
| `/stop-list` | `search` | `name` |
| `/orders` | `search`, `from`, `to` | `-created_at` |
| `/order-attempts` | `search`, `from`, `to`, `reason_code` | `-created_at` |
| `/procurement-recommendations` | `search`, `category_id` | Не принимается; фиксированный приоритет |
| `/hot-offers` | `search` | Не принимается; фиксированный приоритет |
| `/product-categories` | `search` | `name` |
| `/users` | `search`, `role`, `is_active` | `name` |
| `/audit-log` | `actor_id`, `action`, `entity_type`, `entity_id`, `from`, `to` | `-created_at` |
| `/stock-movements` | `product_id`, `batch_id`, `order_id`, `type`, `from`, `to` | `-occurred_at` |
| `/analytics/write-offs` | `from`, `to`, `product_id`, `reason` | Не принимается; по имени продукта |
| `/analytics/ingredient-shortages` | `from`, `to` | Не принимается; по числу отказов убыванию |
| `/analytics/stop-list-forecast` | `lookback_days`, `horizon_hours` | Не принимается; по ближайшему `estimated_stop_at`, null последним |

`/supplies.from/to` ограничивают `created_at`, а не `received_at`. Поиск поставок — по номеру; поиск заказов/отказов использует сохранённые исторические названия согласно README.

### Значения перечисляемых фильтров

| Параметр | Допустимые значения / поведение при отсутствии |
|---|---|
| `/products`, `/dishes`: `is_active` | `all`, `true`, `false`; по умолчанию `true` |
| `/inventory`: `filter` | `all`, `expiring`, `expired`, `out_of_stock`, `deficit` |
| `/products/{id}/batches`: `status` | `all`, `valid`, `expiring`, `expired`, `depleted`; без параметра — все ненулевые партии |
| `/dishes`: `availability` | `all`, `available`, `unavailable` |
| `/users`: `role` | `admin`, `manager`, `storekeeper`, `order_operator`; без параметра — без ограничения по роли |
| `/users`: `is_active` | `true`, `false`; без параметра — без ограничения по активности |
| `/stock-movements`: `type` | `receipt`, `order_consumption`, `expiration`, `manual_writeoff` |
| `/analytics/write-offs`: `reason` | `all`, `expiration`, `manual_writeoff` |

Отсутствие `batches.status` отличается от явного `status=all`: последнее включает и исчерпанные партии. Этот фильтр разбирается только при наличии параметра. Для `/users.is_active` здесь выбран договор: отсутствие означает все записи, переданное значение — `true` или `false`; README не задаёт для этого эндпоинта отдельное значение `all`.

UUID-фильтры (`category_id`, `supply_id`, `actor_id`, `entity_id`, `product_id`, `batch_id`, `order_id`) разбираются через `ParseUUID`, временные границы — через `ParseDateTime`. Значения `action`, `entity_type`, `reason_code` должны проверяться по предметному контракту при реализации соответствующих списков.

Для `/analytics/stop-list-forecast`: `lookback_days` по умолчанию 7, допустимо 1–90; `horizon_hours` по умолчанию 72, допустимо 1–720. Проверка этих специальных диапазонов подключается при реализации прогноза.

### Сортировка

- `sort=name` означает возрастание; `sort=-created_at` — убывание.
- Проверяется вся строка из разрешённого списка: разрешённое `name` не разрешает автоматически `-name`.
- Результат — `dto.Sort{Field, Descending}`. Например, `-created_at` превращается в `{Field: "created_at", Descending: true}`.
- Сортировки по умолчанию для конкретных списков задаются в handler: например, `name` для товаров и `-created_at` для поставок. Для склада и партий выбирается значение из их перечня при реализации списка.
- Для стабильного порядка последним критерием добавляется ID. Для `/inventory.sort=nearest_expires_at` null идёт последним.
- Репозиторий сопоставляет разрешённое имя API с заранее заданной SQL-колонкой. Произвольная строка из запроса не вставляется в SQL.
- Для фиксированного порядка `sort` не включается в список разрешённых query-параметров и `ParseSort` не вызывается.

### Общие правила применения фильтров

- Неизвестные названия и повторные параметры отклоняются.
- Значения по умолчанию используются при отсутствии параметра. Пустое значение сортировки/перечисляемого фильтра не заменяется значением по умолчанию и отклоняется.
- Фильтры объединяются через AND; поиск выполняется без учёта регистра.
- Расчёт `total` учитывает все фильтры и выполняется до пагинации.
- Проверка параметров, применение фильтров в SQL и выдача ошибок подключаются явно при реализации конкретного handler и репозитория.

## Порядок обработки в будущем handler списка

1. Получить `query := c.Request.URL.Query()`.
2. Вызвать `ValidateQuery` с разрешёнными именами конкретного эндпоинта.
3. Разобрать пагинацию через `ParsePagination`.
4. Разобрать сортировку через `ParseSort`, если список принимает `sort`.
5. Разобрать перечисляемые фильтры через `ParseEnum`.
6. При наличии UUID/временных фильтров вызвать `ParseUUID`/`ParseDateTime` и проверить связанные ограничения.
7. После каждого вызова проверить ошибку; при ошибке прекратить предметную обработку.
8. Передать проверенные параметры сервису и репозиторию.
9. Сформировать `dto.ListResponse` либо единый ответ с ошибкой.

Общий механизм разбора и контракт параметров относятся к S02-T02. Применение к бизнес-спискам реализуется в соответствующих предметных стори; request ID, логирование и общее преобразование ошибок — в S02-T03.
