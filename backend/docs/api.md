# Общие правила API

Основной предметный контракт описан в [README](../../README.md#rest-api), структурированный контракт — в [openapi.yaml](openapi.yaml). Базовый путь — `/api/v1`.

В проекте реализованы общие DTO, функции разбора параметров, request ID, HTTP-логирование и единое преобразование ошибок из S02-T01/S02-T02/S02-T03. Зарегистрированы `GET /api/v1/healthcheck`, `GET /api/v1/products`, `GET /api/v1/products/{id}/batches`, `GET /api/v1/inventory`, `POST /api/v1/supplies`, `GET /api/v1/supplies` и `GET /api/v1/supplies/{id}`; неизвестные маршруты обрабатывает общий `NotFound`. Остальные бизнес-списки будут реализованы в соответствующих стори. Их handlers должны явно вызывать функции из `internal/validations`: регистрация пакета сама проверки не подключает.

## OpenAPI-контракт

Файл [openapi.yaml](openapi.yaml) использует OpenAPI 3.0.3 и описывает основные сценарии: healthcheck, выбор продуктов, склад, приём и чтение поставки, выбор блюд, проверку корзины, создание и чтение заказа. Остальные операции из README добавляются в соответствующих стори.

Каждая операция помечена `x-implementation-status`:

- `implemented` — маршрут реализован: healthcheck, выбор продуктов, список партий, агрегаты склада, приёмка, список и детали поставки.
- `planned` — согласованное будущее поведение, маршрут пока недоступен.

Контракт содержит общие схемы, параметры, HTTP-ответы и примеры. UUID и даты примеров иллюстративные: для реального запроса нужны существующие ID и актуальные сроки годности. Количества — строки; `nullable: true` в OpenAPI 3.0 допускает JSON `null`, даже если пример схемы показывает строку. Для необязательных целевых запасов `null` означает отсутствие заданной цели, а не нулевой запас.

Каждая стори, изменяющая API, должна дополнять этот файл в том же изменении:

1. Добавить или обновить метод и путь, параметры, тело запроса и ограничения.
2. Указать схемы успешных ответов и всех предусмотренных ошибок.
3. Добавить примеры запросов, успешных ответов и характерных ошибок.
4. Указать доступные роли и требования авторизации, CSRF и идемпотентности.
5. Изменить статус операции на `implemented` после реализации.
6. Проверить контракт OpenAPI-валидатором и согласованность примеров со схемами.

Маршруты поставок проверяют существующую сессию `flagman_session`, роль, а для POST также CSRF и Origin. Схема `SessionCookie` описана в OpenAPI. Выдача сессий через login, me и logout пока не реализована. Лимит тела запроса и ответы `429` подключены в S02-T05; общие временные параметры добавляются в OpenAPI вместе с использующими их операциями списков.

### Просмотр в Swagger UI

Из корня проекта:

```bash
docker run --rm \
  --name flagman-swagger \
  -p 127.0.0.1:8090:8080 \
  -e SWAGGER_JSON=/docs/openapi.yaml \
  -v "$PWD/backend/docs:/docs:ro" \
  docker.swagger.io/swaggerapi/swagger-ui
```

Документация доступна на `http://localhost:8090`. Для выполнения запросов через `Try it out` требуется настроить доступ к backend: относительный сервер `/api/v1` на этом адресе указывает на контейнер Swagger. Можно проксировать API на том же origin либо выбрать абсолютный API-сервер и настроить CORS. Отображение Swagger UI не заменяет полную проверку контракта.

## Ответ со списком

Структура: `dto.ListResponse[T]`, где `T` — тип одного элемента.

| Поле | Значение |
|---|---|
| `items` | Элементы текущей страницы; пустой список — `[]` |
| `total` | Количество записей после всех фильтров, до пагинации |
| `page` | Номер возвращённой страницы, начиная с 1 |
| `page_size` | Размер страницы, по умолчанию 50, максимум 100 |
| `meta` | Дополнительные сведения о выборке; без них — `{}` |

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 50,
  "meta": {}
}
```

Для ответов с расчётами `meta.server_time` задаёт момент расчёта в UTC. В `meta` также может передаваться `request_id`. Область расчёта каждого агрегата в `meta` должна быть описана в контракте конкретного эндпоинта.

Handler должен инициализировать пустые срезы и maps: нулевые значения этих полей сериализуются как `null`, а DTO сама не заменяет их на `[]` и `{}`. Одиночный ресурс возвращается напрямую.

## Ошибки

Внутренняя ошибка валидации: `validations.FieldError{Field, Message}`. Она содержит путь поля, например `page` или `items[0].quantity`, и объяснение ошибки. Функции разбора возвращают первую найденную ошибку; HTTP-ответ формирует handler.

### Структура ответа

Текущая `dto.ErrorResponse` соответствует README и OpenAPI: вложенный объект `error` и `request_id` в корне. Ошибки полей передаются в `error.details.fields`:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные",
    "details": {
      "fields": [
        {
          "path": "page",
          "code": "invalid_value",
          "message": "Ожидается целое число больше нуля"
        }
      ]
    }
  },
  "request_id": "99999999-9999-4999-8999-999999999999"
}
```

| Поле | Значение |
|---|---|
| `error.code` | Стабильный машинный код ошибки |
| `error.message` | Описание для пользователя |
| `error.details` | Дополнительные сведения; без них — `{}` |
| `error.details.fields` | Список нарушений с `path`, `code`, `message`; при ошибке валидации |
| `request_id` | UUID текущего запроса, совпадающий с заголовком `X-Request-ID` и ID в логах |

Общий `handler.writeError` регистрирует исходную ошибку в `c.Errors`, затем вызывает `makeErrorResponse` и отправляет ответ через `AbortWithStatusJSON`. Если ответ уже начат, функция не пытается повторно изменить его статус и тело. Handler после `writeError(c, err)` должен сделать `return`, чтобы прекратить выполнение своего кода.

`validations.FieldError` преобразуется через `errors.As`, доменные ошибки из `internal/errors` — через `errors.Is`. Обёртки с `fmt.Errorf("...: %w", err)` сохраняют это поведение. Текущий код поля для общей `FieldError` — `invalid_value`; предметные коды дополняются при реализации соответствующих стори.

### HTTP-статусы

| Ситуация | Статус |
|---|---:|
| Невалидный JSON (`INVALID_JSON`) | 400 |
| Нет авторизации (`UNAUTHORIZED`) | 401 |
| Недостаточно прав (`FORBIDDEN`) | 403 |
| Ресурс не найден (`NOT_FOUND`) | 404 |
| Конфликт состояния (`CONFLICT`) | 409 |
| Неверные значения полей, query-параметров, фильтров или сортировки (`VALIDATION_ERROR`) | 422 |
| Внутренний сбой (`INTERNAL_ERROR`) | 500 |
| Временная недоступность (`SERVICE_UNAVAILABLE`) | 503 |

Это таблица реализованного общего преобразования ошибок. Маршруты поставок используют эти коды, включая отдельный `400 INVALID_JSON` для синтаксических ошибок и `422` для ошибок полей. Неизвестная ошибка даёт безопасный `500`, а её исходная причина записывается в лог. Внутренние SQL-сведения клиенту не возвращаются.

### Отсутствующий ресурс

Неизвестные маршруты подключены через `mux.NoRoute(handler.NotFound)` и используют тот же `writeError`, что будут использовать бизнес-handlers:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Ресурс не найден",
    "details": {}
  },
  "request_id": "99999999-9999-4999-8999-999999999999"
}
```

- Корректный UUID отсутствующего запрошенного ресурса — `404 NOT_FOUND`.
- Неверный UUID — `422 VALIDATION_ERROR`.
- Пустой результат списка — `200`, `items: []`, `total: 0`.
- Неверная ссылка в теле запроса — `422` с путём поля, согласно README.

`GET /supplies/{id}` преобразует отсутствие строки в `ErrNotFound`; неожиданный сбой БД остаётся внутренней ошибкой. Остальные бизнес-методы чтения следуют этому правилу при реализации. Пустую выборку списка нельзя преобразовывать в `ErrNotFound`.

## Request ID и логирование

В `main.go` подключена цепочка `RequestID → RequestLogger → Recovery`. Реализация middleware находится в `internal/handler/middleware.go`, работа с ID в стандартном контексте — в `internal/requestctx/context.go`.

- `RequestID` генерирует новый UUID, сохраняет его через `requestctx.WithID` в `c.Request.Context()` и устанавливает заголовок ответа `X-Request-ID`.
- `requestctx.ID(ctx)` позволяет получить тот же ID в handler или сервисе. Контекст запроса передаётся далее явно; сервису не требуется зависимость от Gin.
- `RequestLogger` после выполнения цепочки записывает `request_id`, `method`, шаблон `route`, `status` и `duration`. Для неизвестного маршрута `route` равен `unmatched`. Если ошибка зарегистрирована в `c.Errors`, её причина добавляется в лог.
- Успешные запросы логируются на `Info`, ответы `4xx` — на `Warn`, ответы `5xx` — на `Error`. Ошибка после уже отправленного успешного статуса тоже логируется на `Error`.
- `Recovery` перехватывает panic внутри цепочки, пишет причину и stack trace с ID в серверный лог и использует общий безопасный ответ `500`, если ответ ещё не начат.

Request ID не является бизнес-ID, токеном авторизации или ключом идемпотентности. При повторе идемпотентной записи `Idempotency-Key` остаётся прежним, а новый HTTP-запрос получает новый request ID в заголовке. Сохранённое тело ответа возвращается без изменений, включая ID исходного запроса, если он есть в теле. Заголовок `X-Request-ID` относится к текущему HTTP-запросу и никогда не восстанавливается из `idempotency_keys`.

## Общий разбор параметров

| Функция | Назначение |
|---|---|
| `ValidateQuery(query, allowed...)` | Проверка разрешённых названий параметров и запрет повторов |
| `ParsePagination(query)` | Получение проверенных `dto.Pagination` |
| `ParseSort(query, defaultValue, allowed...)` | Получение проверенной `dto.Sort` |
| `ParseEnum(query, field, defaultValue, allowed...)` | Проверка значения из заданного списка |
| `ParseUUID(field, raw)` | Разбор идентификатора в `uuid.UUID` |
| `ParseDateTime(field, raw)` | Разбор временной отметки в `time.Time` с приведением к UTC |
| `ParseQuantity(field, raw)` | Разбор неотрицательного количества в `int64` в тысячных долях |

`ValidateQuery` проверяет названия и число значений. Тип и содержимое каждого параметра проверяются отдельным разбором. Сначала handler проверяет ошибку, затем использует возвращённый результат.

Списки допустимых параметров, сортировок и значений фильтров передаются конкретным handler. Значение по умолчанию для `ParseSort`/`ParseEnum` должно входить в разрешённый список.

### Пагинация

| Параметр | При отсутствии | Ограничение |
|---|---:|---|
| `page` | 1 | Целое число больше нуля |
| `page_size` | 50 | Целое число от 1 до 100 |

Неверные значения не заменяются значениями по умолчанию. `page=`, `page=abc`, `page=0`, `page_size=101` и повторные параметры отклоняются.

Результат разбора — `dto.Pagination{Page, PageSize}`. Ограничение выборки и безопасный расчёт смещения выполняются при реализации репозитория.

### UUID

Принимается строка из 36 символов в формате `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`; допускаются заглавные и строчные шестнадцатеричные символы. Запись без дефисов, пробелы и пустая строка отклоняются.

Результат — `github.com/google/uuid.UUID`. Парсер проверяет формат; существование сущности проверяется отдельно. Парсер не ограничивает версию UUID и не запрещает нулевой UUID.

### Дата и время

Разбор выполняется через `time.Parse(time.RFC3339Nano, raw)`. Требуется временная отметка с часовым смещением или `Z`; дробные секунды поддерживаются. Результат приводится к UTC.

```text
2026-10-10T15:30:00+03:00 -> 2026-10-10T12:30:00Z
2026-10-10T12:30:00.123Z  -> допустимо
2026-10-10T15:30:00      -> ошибка: отсутствует timezone
2026-02-30T12:30:00Z     -> ошибка: несуществующая дата
```

Необязательный временной фильтр разбирается только при наличии параметра. Временные ограничения предметной операции и проверка порядка границ выполняются отдельно. Для интервала `from` включительно, `to` исключительно; если обе границы переданы, `from` не должен быть позже `to`.

В URL знак `+` в часовом смещении должен быть закодирован как `%2B`; удобно формировать query через `url.Values.Encode()`. Можно использовать UTC с `Z`.

### Точные количества

В JSON количество передаётся строкой, например `"12.375"`. Текущий парсер принимает запись по шаблону `^\d{1,11}(\.\d{1,3})?$`:

- От 1 до 11 цифр до точки; ведущие нули также учитываются при проверке длины.
- От 1 до 3 цифр после точки, если точка присутствует.
- Только неотрицательные значения, включая ноль.
- Без пробелов, знака `+`, запятой и экспоненциальной записи.
- Лишние дробные знаки отклоняются без округления.

Ограничения соответствуют диапазону неотрицательных значений `numeric(14,3)`: максимум `99999999999.999`. Входной JSON-тип строки обеспечивается DTO конкретного запроса; `ParseQuantity` получает уже строку.

Результат — целое число в тысячных долях:

| Вход | Результат |
|---|---:|
| `"12"` | 12000 |
| `"12.5"` | 12500 |
| `"12.375"` | 12375 |
| `"0.001"` | 1 |
| `"0"` | 0 |

Преобразование через `float64` не используется. Перед записью в `numeric(14,3)` и выдачей JSON необходимо учитывать масштаб 1000: внутреннее значение 12375 означает `"12.375"`. Общая функция обратного форматирования пока не добавлена.

Положительность количества для приёмки/списания проверяется отдельно. Для единицы `pcs` количество должно быть целым: `quantity % 1000 == 0`. Знаковые изменения остатков (`delta_quantity`) требуют отдельного представления/форматирования; `ParseQuantity` предназначен для неотрицательных входных количеств.

Во всех перечисленных ниже коллекциях допустимы `page` и `page_size`. В таблице перечислены дополнительные фильтры; `sort` разрешён только там, где задан его допустимый список.

| Эндпоинт после `/api/v1` | Дополнительные фильтры | Допустимый `sort` |
|---|---|---|
| `/products` | `search`, `category_id`, `is_active` | `name` |
| `/inventory` | `search`, `category_id`, `filter` | `name`, `nearest_expires_at` |
| `/products/{id}/batches` | `status`, `supply_id` | `expires_at`, `-created_at` |
| `/supplies` | `search`, `from`, `to` | `-created_at` |
| `/dishes` | `search`, `is_active`, `availability` | `name` |
| `/stop-list` | `search` | `name` |
| `/orders` | `search`, `from`, `to` | `-created_at` |
| `/order-attempts` | `search`, `from`, `to`, `reason_code` | `-created_at` |
| `/procurement-recommendations` | `search`, `category_id` | Не принимается; фиксированный приоритет |
| `/hot-offers` | `search` | Не принимается; фиксированный приоритет |
| `/product-categories` | `search` | `name` |
| `/users` | `search`, `role`, `is_active` | `name` |
| `/audit-log` | `actor_id`, `action`, `entity_type`, `entity_id`, `from`, `to` | `-created_at` |

### Значения перечисляемых фильтров

| Параметр | Допустимые значения / поведение при отсутствии |
|---|---|
| `/products`, `/dishes`: `is_active` | `all`, `true`, `false`; по умолчанию `true` |
| `/inventory`: `filter` | `all`, `expiring`, `expired`, `out_of_stock`, `deficit` |
| `/products/{id}/batches`: `status` | `all`, `valid`, `expiring`, `expired`, `depleted`; без параметра — все ненулевые партии |
| `/dishes`: `availability` | `all`, `available`, `unavailable` |
| `/users`: `role` | `admin`, `manager`, `storekeeper`, `order_operator`; без параметра — без ограничения по роли |
| `/users`: `is_active` | `true`, `false`; без параметра — без ограничения по активности |
| `/stock-movements`: `type` | `receipt`, `order_consumption`, `expiration`, `manual_writeoff` |
| `/analytics/write-offs`: `reason` | `all`, `expiration`, `manual_writeoff` |

Отсутствие `batches.status` отличается от явного `status=all`: последнее включает и исчерпанные партии. Этот фильтр разбирается только при наличии параметра. Для `/users.is_active` здесь выбран договор: отсутствие означает все записи, переданное значение — `true` или `false`; README не задаёт для этого эндпоинта отдельное значение `all`.

UUID-фильтры (`category_id`, `supply_id`, `actor_id`, `entity_id`, `product_id`, `batch_id`, `order_id`) разбираются через `ParseUUID`, временные границы — через `ParseDateTime`. Значения `action`, `entity_type`, `reason_code` должны проверяться по предметному контракту при реализации соответствующих списков.

Для `/analytics/stop-list-forecast`: `lookback_days` по умолчанию 7, допустимо 1–90; `horizon_hours` по умолчанию 72, допустимо 1–720. Проверка этих специальных диапазонов подключается при реализации прогноза.

### Сортировка

- `sort=name` означает возрастание; `sort=-created_at` — убывание.
- Проверяется вся строка из разрешённого списка: разрешённое `name` не разрешает автоматически `-name`.
- Результат — `dto.Sort{Field, Descending}`. Например, `-created_at` превращается в `{Field: "created_at", Descending: true}`.
- Сортировки по умолчанию для конкретных списков задаются в handler: например, `name` для товаров и `-created_at` для поставок. Для склада и партий выбирается значение из их перечня при реализации списка.
- Для стабильного порядка последним критерием добавляется ID. Для `/inventory.sort=nearest_expires_at` null идёт последним.
- Репозиторий сопоставляет разрешённое имя API с заранее заданной SQL-колонкой. Произвольная строка из запроса не вставляется в SQL.
- Для фиксированного порядка `sort` не включается в список разрешённых query-параметров и `ParseSort` не вызывается.

### Общие правила применения фильтров

- Неизвестные названия и повторные параметры отклоняются.
- Значения по умолчанию используются при отсутствии параметра. Пустое значение сортировки/перечисляемого фильтра не заменяется значением по умолчанию и отклоняется.
- Фильтры объединяются через AND; поиск выполняется без учёта регистра.
- Расчёт `total` учитывает все фильтры и выполняется до пагинации.
- Проверка параметров, применение фильтров в SQL и выдача ошибок подключаются явно при реализации конкретного handler и репозитория.

## Порядок обработки в будущем handler списка

1. Получить `query := c.Request.URL.Query()`.
2. Вызвать `ValidateQuery` с разрешёнными именами конкретного эндпоинта.
3. Разобрать пагинацию через `ParsePagination`.
4. Разобрать сортировку через `ParseSort`, если список принимает `sort`.
5. Разобрать перечисляемые фильтры через `ParseEnum`.
6. При наличии UUID/временных фильтров вызвать `ParseUUID`/`ParseDateTime` и проверить связанные ограничения.
7. После каждого вызова проверить ошибку; при ошибке вызвать `writeError(c, err)` и сделать `return`.
8. Передать проверенные параметры сервису и репозиторию.
9. Сформировать `dto.ListResponse` либо единый ответ с ошибкой.

Общий механизм разбора и контракт параметров относятся к S02-T02, подключённые request ID, логирование и преобразование ошибок — к S02-T03, стартовый OpenAPI и правило единого `404` — к S02-T04. Применение этих механизмов к бизнес-спискам реализуется в соответствующих предметных стори вместе с обновлением OpenAPI.

## Транзакционные аудит и outbox — S03-T05

Реализованы операции `Repository.AppendAudit(ctx, tx, entry)` и `Repository.AppendOutbox(ctx, tx, event)`. Их контракт включён в интерфейс repository, используемый service. Типы записей и безопасных снимков находятся в `internal/model/events.go`, SQL и проверки — в `internal/repository/events.go`.

Обе операции требуют явно переданный `pgx.Tx`, полученный, например, внутри `WithinTx`. Передача пула, `nil` или указателя на nil-транзакцию возвращает `repository.ErrTransactionRequired`. Завершённую транзакцию отклоняет pgx при выполнении SQL. Helpers не открывают отдельную транзакцию и не вызывают commit: предметные записи, аудит и outbox должны использовать один и тот же `tx`.

### Автор, request ID и время

- `ActorID` передаётся сервисом из проверенной сервером личности пользователя. Его нельзя брать из JSON запроса. `nil` означает системную операцию; нулевой UUID отклоняется. Автор проверяется FK на `users` при вставке.
- `request_id` берётся из `requestctx.ID(ctx)`. HTTP middleware уже устанавливает его в контекст. Для фоновой операции можно назначить собственный ID через `requestctx.WithID`; если ID отсутствует, в аудите сохраняется SQL `NULL`, а поле в payload outbox опускается.
- Request ID ограничен 128 символами согласно схеме; невалидный UTF-8 и нулевой символ отклоняются.
- `created_at` задаётся базой через `clock_timestamp()`. `occurred_at` в payload outbox задаётся сервером в UTC при подготовке события. Эти поля не принимаются из клиентского запроса.

### Разрешённые данные аудита

`AuditEntry.Before` и `AuditEntry.After` принимают только конкретные указатели на перечисленные ниже снимки. Repository проверяет точный тип снимка и его соответствие `EntityType` перед JSON-сериализацией. Maps, произвольный JSON, расширенные структуры с дополнительными полями и собственными JSON-marshalers не принимаются.

| EntityType | Тип снимка | Разрешённые поля |
|---|---|---|
| `product_category` | `CategoryAuditSnapshot` | `name`, `revision` |
| `product` | `ProductAuditSnapshot` | `name`, `category_id`, `unit`, `display_unit`, `standard_shelf_life_hours`, `target_stock`, `is_active`, `revision` |
| `dish` | `DishAuditSnapshot` | `name`, `description`, `is_active`, `revision`, `recipe_version_id`, `recipe_version`, `recipe` с `product_id` и `quantity_per_portion` |
| `supply` | `SupplyAuditSnapshot` | `number`, `received_at`, `batches` с ID, номером строки, количествами и параметрами срока годности |
| `order` | `OrderAuditSnapshot` | `number`, `items` с ID блюда/версии рецепта, снимком названия и порциями |
| `stock_movement` | `StockMovementAuditSnapshot` | `batch_id`, `order_item_id`, `type`, `delta_quantity`, `remaining_quantity_after`, `product_name_snapshot`, `unit_snapshot`, `note` |
| `user` | `UserAuditSnapshot` | `name`, `email`, `role`, `is_active`, `revision` |
| `settings` | `SettingsAuditSnapshot` | `restaurant_name`, `timezone`, `expiring_threshold_hours`, `auto_writeoff_expired`, `revision` |

Количество в снимках задаётся строками. Снимки строятся явно из уже проверенных/сохранённых данных; helpers не заменяют предметную проверку количеств, порций или сроков. Даты в снимках следует передавать в UTC, а пустые коллекции инициализировать как `[]`.

Для всех объектов, кроме singleton-настроек, нужен ненулевой `EntityID`. Для `settings` передаётся `EntityID: nil`, поскольку ID настроек в схеме — integer `1`, а поле ID объекта аудита — UUID.

| Action | Разрешённые EntityType |
|---|---|
| `create` | `product_category`, `product`, `dish`, `supply`, `order`, `user` |
| `update` | `product_category`, `product`, `dish`, `user`, `settings` |
| `password_change` | `user` |
| `manual_writeoff`, `expiration` | `stock_movement` |

Для `create` поле `Before` отсутствует. Для `update` и `password_change` нужны оба снимка. `After` обязателен для всех разрешённых действий. Отсутствующий `Before` сохраняется как SQL `NULL`; указатель на nil-снимок внутри интерфейса отклоняется.

В снимках нет полей `password`, `password_hash`, `initial_password`, `new_password`, токенов сессии/CSRF, cookie или заголовков авторизации. Для смены пароля сохраняются действие и разрешённые пользовательские поля, например изменившаяся ревизия. Передавать секреты через разрешённые текстовые поля тоже нельзя: сервис формирует снимок из конкретных предметных полей, а не из полного запроса или модели хранения.

### Разрешённые события и темы outbox

`OutboxEvent` принимает тип события, автора и списки UUID. Произвольного `payload` или параметра `topics` в операции записи нет. Repository формирует `OutboxPayload`: `occurred_at`, необязательный `request_id`, `topics` и непустые списки `product_ids`, `batch_ids`, `dish_ids`, `category_ids`, `supply_ids`, `order_ids`, `user_ids`. Нулевые UUID отклоняются.

Базовые темы пересчёта склада: `inventory`, `batches`, `dashboard`, `dishes`, `stop-list`, `hot-offers`, `procurement-recommendations`.

| EventType | Темы |
|---|---|
| `inventory.changed` | Базовые темы и `stock-movements`; при наличии `supply_ids` добавляется `supplies`, при `order_ids` — `orders` |
| `inventory.time_changed` | Базовые темы |
| `products.changed` | Базовые темы и `products` |
| `product_categories.changed` | `product-categories`, `products` |
| `dishes.changed` | `dishes`, `stop-list`, `hot-offers`, `dashboard`, `procurement-recommendations` |
| `settings.changed` | Базовые темы и `settings` |
| `users.changed` | `users`; нужен хотя бы один `user_ids`, остальные списки ID запрещены |

Неизвестные типы событий отклоняются. `user_ids` разрешены только в событии `users.changed`. Чтобы расширить список событий, полей или тем, нужно явно изменить типы, правила repository и этот контракт.

`cursor` и `published_at` при вставке не задаются и остаются SQL `NULL`. Sequence cursor вызывает будущий сериализованный диспетчер после commit предметной транзакции. Запись outbox не отправляет SSE и не назначает номер доставки.

Outbox — внутреннее хранилище. При реализации SSE диспетчер должен отфильтровать темы и соответствующие списки ID по роли получателя; нельзя отправлять сохранённый payload всем пользователям без проекции доступа. До реализации SSE это ограничение относится к будущему коду доставки.

### Подключение к предметной операции

Следующий фрагмент выполняется в service после создания поставки, партий и движений через тот же `tx`. `actorID` — проверенный автор, `supplyID`, `productIDs`, `batchIDs` и `snapshot` — результаты предметной операции:

```go
return s.repo.WithinTx(ctx, nil, func(tx repository.DBTX) error {
    // Здесь создаются поставка, партии и движения через этот же tx.

    if err := s.repo.AppendAudit(ctx, tx, &model.AuditEntry{
        ActorID:    actorID,
        Action:     model.AuditCreate,
        EntityType: model.AuditSupply,
        EntityID:   &supplyID,
        After:      snapshot, // *model.SupplyAuditSnapshot
    }); err != nil {
        return err
    }

    return s.repo.AppendOutbox(ctx, tx, &model.OutboxEvent{
        Type:       model.InventoryChanged,
        ActorID:    actorID,
        ProductIDs: productIDs,
        BatchIDs:   batchIDs,
        SupplyIDs:  []uuid.UUID{supplyID},
    })
})
```

Ошибка любой записи должна возвращаться из callback: тогда `WithinTx` откатывает всю предметную операцию. Ошибки SQL остаются внутренними; существующий HTTP handler возвращает общий `INTERNAL_ERROR`, а не текст PostgreSQL.

Helpers подготовлены в S03-T05 и подключены к созданию поставки в S05-T03 и HTTP-приёмке в S05-T05. Подключение к заказам, изменениям справочников/настроек и списаниям выполняется вместе с соответствующими предметными стори. SSE-диспетчер пока не реализован.

## Атомарная приёмка поставки — S05-T03

Операция `internal/service/supply.Service.Create(ctx, actorID, input)` подключена в `cmd/api/main.go` и доступна через `service.CreateSupply`. Сервис получает предметный repository и общие транзакционные helpers отдельными зависимостями. `actorID` — UUID пользователя, проверенного вызывающим кодом; поле автора отсутствует в DTO. Нулевой UUID отклоняется до обращения к БД. Проверка прав роли выполняется вызывающим кодом при подключении авторизации и HTTP handler.

Внутри одного `WithinTx` операция:

1. Проверяет запрос, читает и блокирует все уникальные продукты через `ORDER BY id FOR UPDATE`, независимо от порядка строк в запросе. Блокировки удерживаются до завершения транзакции; передача пула вместо транзакции запрещена.
2. Фиксирует серверное время **после получения блокировок**, проверяет активность продуктов, количество и срок каждой партии по правилам S05-T01/T02.
3. Создаёт поставку с нормализованным номером и автором. `created_at` возвращается из PostgreSQL. Помимо предварительной проверки номера, нарушение `supplies_number_key` преобразуется в `ErrConflict`, включая гонку поставок разных продуктов.
4. Создаёт отдельную партию на каждую исходную строку в исходном порядке (`line_number` начинается с 1), даже если продукт повторяется. Начальный и текущий остатки равны принятому количеству; фактический срок и параметры его расчёта сохраняются в партии.
5. Для каждой партии добавляет одно положительное движение `receipt`: `delta_quantity` и `remaining_quantity_after` равны принятому количеству, `actor_id` равен автору поставки, `occurred_at` равен `received_at`. Название и единица продукта копируются из заблокированной записи в неизменяемый снимок движения.
6. Добавляет один аудит `create/supply` с безопасным снимком всех партий и одно событие `inventory.changed` с ID поставки, всех партий и уникальных продуктов. `request_id` берётся из контекста общими helpers; cursor и published_at остаются пустыми.

Ошибка проверки, любого INSERT или commit возвращает пустой результат и ошибку. Ошибка callback откатывает все предметные записи, аудит и outbox. Успешный результат `model.CreatedSupply` возвращается только после commit. Идемпотентный вход добавлен в S05-T04; HTTP handler, проверка сессии и проекция `SupplyDetail` подключены в S05-T05.

Интеграционные тесты применяют реальные миграции в отдельной случайной схеме и удаляют только её. Для их запуска укажите адрес **тестовой** PostgreSQL в `SUPPLY_TEST_DATABASE_URL` и выполните из `backend`:

```sh
go test -count=1 -v ./internal/service/supply -run Integration
```

Без этой переменной интеграционные тесты пропускаются. Проверяются сохранение и согласованность журнала, снимки аудита/outbox, полный откат на каждом этапе записи и при ошибке commit, отказ всей поставки из-за одной неверной строки, конкурентный дубликат номера, реальный порядок блокировок и проверка срока после ожидания блокировки.

## Общая идемпотентность записи — S05-T04

Типы области и сохранённого ответа находятся в `internal/model/idempotency.go`, SQL — в `internal/repository/idempotency.go`, общий исполнитель — в `internal/service/idempotency`. Изменения схемы не нужны: существующая колонка `endpoint` содержит **метод и путь**, например `POST /api/v1/supplies`; уникальность задаётся `(user_id, endpoint, key)`.

`Service.Execute(ctx, scope, rawBody, operation)` получает UUID проверенного пользователя, HTTP-метод, канонический путь конкретного ресурса без query/fragment и ненулевой UUID ключа. Путь задаёт сервер; для операций над разными объектами он включает ID объекта, а не шаблон маршрута. Авторизация должна выполняться до исполнителя, в том числе при повторе завершённого запроса. `ReadIdempotencyKey` проверяет наличие ровно одного заголовка `Idempotency-Key` и формат UUID.

До запуска callback и любых предметных блокировок исполнитель внутри транзакции `READ COMMITTED` получает неблокирующую `pg_try_advisory_xact_lock` по хешу всей области. Блокировка общая для всех экземпляров приложения, не требует незавершённой строки в таблице и автоматически освобождается при commit/rollback.

| Состояние области | Результат |
|---|---|
| Выполнение в другой транзакции ещё не завершено | `409 REQUEST_IN_PROGRESS`, `Retry-After: 1`, без ожидания предметных блокировок |
| Завершённый ключ, тот же SHA-256 тела | Сохранённые статус, тело и `Location`; callback не вызывается |
| Завершённый ключ, другой SHA-256 тела | `409 IDEMPOTENCY_CONFLICT`; callback не вызывается |
| Ключ отсутствует или истёк | Выполнение callback и сохранение нового завершённого результата |

Хеш считается по **исходным байтам тела**, без нормализации JSON. Изменение пробелов или порядка JSON-полей меняет хеш. Пока первый запрос выполняется, повтор, прошедший ранние проверки, получает `REQUEST_IN_PROGRESS`; сравнение с сохранённым хешем выполняется после завершения первого запроса. Разные пользователи, методы, пути или UUID ключа образуют независимые области.

Завершённый результат сохраняется вместе с предметными изменениями в одной внешней транзакции. Callback выполняется внутри savepoint и возвращает `idempotency.Outcome`:

- `Response` содержит HTTP-статус `200–499`, JSON-тело и необязательный `Location`.
- `Rollback: false` сохраняет предметные факты вместе с ответом: например, будущий отказ заказа `409` может сохранить одну `order_attempt`.
- `Rollback: true` для ответа `4xx` отменяет предметные записи до savepoint, но сохраняет завершённый отказ. Это позволяет восстановить транзакцию даже после SQL-конфликта номера поставки.
- Возвращённая ошибка означает технический сбой: вся внешняя транзакция откатывается, завершённого ключа нет. Повтор может выполнить операцию заново. Ответы `5xx`, ошибка сериализации, отмена контекста и ошибка commit не создают завершённого результата.

В `response_headers` сохраняется только `Location`: cookie, токены, авторизационные заголовки, `Retry-After` и `X-Request-ID` туда не копируются. Исходное тело запроса не сохраняется и не логируется механизмом; хранится SHA-256. Callback должен формировать безопасную проекцию ответа, а не сериализовать модели с секретами.

Поскольку `response_body` имеет тип JSONB, первый запрос также получает тело из `INSERT ... RETURNING`, уже в представлении PostgreSQL. Поэтому повтор возвращает те же байты, а не только эквивалентный JSON. Для статусов без тела (`204`, `205`, `304`) в БД хранится JSON `null`, наружу возвращается пустое тело. `WriteIdempotencyResponse` отправляет сохранённое тело без повторной сериализации и восстанавливает `Location`.

Срок хранения результата — **минимум 24 часа от сохранения**, по часам PostgreSQL (`expires_at` задаётся как текущее время плюс 24 часа). Истёкшая строка не участвует в повторе и заменяется при следующем выполнении той же области. Активная завершённая строка не перезаписывается. Для корректного повторного использования ключа запуск очистки не требуется; фоновая очистка освобождает место.

### Подключение к поставке

В `cmd/api/main.go` общий исполнитель передан сервису поставок. `supply.Service.CreateIdempotent(ctx, actorID, key, rawBody, render)` используется методом `Receive`, которому делегирует `service.CreateSupplyIdempotent`:

1. Используют область `POST /api/v1/supplies`.
2. До транзакции разбирают JSON и выполняют независимые от БД проверки входных данных. Внутри callback после блокировки области проверяют продукты, сроки по текущему времени, номер и выполняют атомарную запись S05-T03.
3. Строят успешное тело через `ResponseRenderer`, которому доступны созданная поставка и тот же `tx`. `Receive` читает и сериализует проекцию `SupplyDetail` до commit.
4. Сохраняют `201` и `Location: /api/v1/supplies/{id}` либо завершённый предметный отказ `409/422` с общим форматом ошибок из `errors.MakeResponse`. Ранние `400/401/403/413/422` не сохраняются.

Обычный `Create` остаётся внутренней операцией без HTTP-идемпотентности; POST вызывает `Receive` через `CreateSupplyIdempotent`.

Тесты S05-T04 запускаются тем же способом, что и S05-T03: `SUPPLY_TEST_DATABASE_URL` указывает на отдельную тестовую PostgreSQL, затем `go test -race -count=1 ./...` из `backend`. Проверяются точный повтор статуса/тела/Location, сохранённые отказы и факты, конфликт тела, параллельный запрос до продуктовых блокировок, независимость всех частей области, истечение ключа, rollback при сбое outbox/записи результата/commit/сериализации и освобождение ключа после отмены запроса. HTTP-тесты проверяют обязательный UUID, код `REQUEST_IN_PROGRESS`, `Retry-After` и новый `X-Request-ID` при неизменном теле повтора.

## HTTP-приёмка и детали поставки (S05-T05)

`POST /api/v1/supplies` принимает `CreateSupplyRequest`, требует UUID в `Idempotency-Key` и `Content-Type: application/json`. У POST и GET деталей нет query-параметров: любой параметр даёт `422`. Handler находится в `internal/handler/supply`, проверка доступа — в `internal/handler/auth`, предметная операция и проекция — в `internal/service/supply`.

Автор определяется по cookie `flagman_session`: в `sessions.token_hash` хранится SHA-256 непрозрачного токена. Отозванная или истёкшая сессия и неактивный пользователь дают `401`. Роли `admin`, `manager`, `storekeeper` допущены к обеим операциям; `order_operator` получает `403`. POST требует точный `X-CSRF-Token` сессии и `Origin`, совпадающий с `FRONTEND_ORIGIN`. Значение по умолчанию — `http://flagman.localhost`; для другого frontend задайте его origin в существующем `infrastructure/.env`. Заголовки с ID пользователя не используются для авторизации.

Реализовано чтение существующих сессий. Маршруты login/me/logout остаются отдельной задачей; HTTP-тесты создают сессии только в изолированных тестовых схемах.

Успех возвращает `201`, JSON `SupplyDetail` и `Location: /api/v1/supplies/{id}`. Детали содержат нормализованный номер, даты, автора (`id`, `name`), продукты, все партии в порядке исходных строк, точные количества в базовых единицах и фактические сроки годности. Поля отсутствующего `produced_at` и `shelf_life_hours` возвращаются как `null`. Пароли, хеши и сессионные токены в эту проекцию не входят.

`meta.server_time` — единственное время расчёта статусов партий, зафиксированное после продуктовых блокировок. При нулевом остатке статус `depleted`; иначе `expired` при `expires_at <= T`, затем `expiring` в пределах включительно порога ресторана, иначе `valid`. `remaining_seconds` — округлённая вниз знаковая разница между сроком и `T`, в том числе для израсходованных партий. Все даты ответа — UTC; порог читается из `restaurant_settings` (24 часа, если настройки ещё не созданы).

Поставка, партии, движения, аудит, outbox, построение JSON и сохранение результата идемпотентности выполняются в общей транзакции. Handler получает успешный ответ только после commit. Сбой outbox, чтения проекции, сериализации или commit даёт безопасный `500` без `Location` и без частичных записей. Просроченная строка даёт `422` с полным откатом предметных записей и сохранением завершённого отказа. Дубликат номера, включая конкурентную гонку разных ключей, даёт `409 CONFLICT`.

`GET /api/v1/supplies/{id}` возвращает `200` в той же схеме, читая метаданные, настройки и партии в транзакции `REPEATABLE READ READ ONLY`. Включаются израсходованные партии; остатки и статусы отражают текущий снимок. Отсутствующий UUID даёт `404`, неверный UUID — `422`. Повтор POST возвращает первоначальные значения, включая `meta.server_time`, даже если текущие детали уже изменились.

В `internal/service/supply/http_integration_test.go` настоящий HTTP-сервер проверяется с PostgreSQL: `201` и переход по `Location`, дубликат номера и его конкурентная гонка, откат всей поставки при ошибке последней строки или техническом сбое, параллельный повтор с `REQUEST_IN_PROGRESS` и `Retry-After: 1`, конфликт изменённого тела и свежий request ID. Отдельный тест закрывает TCP-соединение после успешного commit до передачи тела ответа: повтор возвращает сохранённые байты и `Location`, не добавляя поставок, партий, движений, аудита и outbox.

Запуск из `backend` с отдельной тестовой PostgreSQL:

```bash
SUPPLY_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./...
```

Каждый интеграционный тест создаёт отдельную схему с миграциями и удаляет её после проверки. Без `SUPPLY_TEST_DATABASE_URL` эти тесты пропускаются; unit-тесты продолжают запускаться.

## Срок хранения и очистка идемпотентности (S05-T06)

Результат используется только при `expires_at > clock_timestamp()`. При равенстве или истечении срока ключ может считаться новой попыткой, в том числе с другим телом. Повтор до истечения срока возвращает сохранённый ответ и не продлевает срок хранения. Это правило применяется к успешным результатам и завершённым предметным отказам.

`idempotency.Service.CleanupExpired` удаляет только записи `idempotency_keys` с `expires_at <= statement_timestamp()`. Каждая транзакция удаляет максимум 1000 строк, упорядоченных по сроку и ID. `FOR UPDATE SKIP LOCKED` пропускает занятые строки, позволяя нескольким backend выполнять очистку параллельно с записью результатов. Активный результат не удаляется. Существующий индекс `idempotency_keys_expires_at_idx` поддерживает выборку; новые миграции не нужны.

В `cmd/api/main.go` очистка запускается сразу и затем раз в минуту. У каждой партии удаления есть таймаут 5 секунд. При остановке приложения контекст отменяется, backend ждёт завершения worker перед закрытием пула БД. Ошибка очистки логируется, следующая попытка происходит через минуту. Просроченный кеш может оставаться в БД дольше 24 часов, но уже не участвует в повторах.

`order_attempts` — самостоятельная история отказов, которую очистка кеша не удаляет. Поставки, движения, аудит и outbox также сохраняются. После истечения ключа новая предметная попытка может создать новый отказ; старый снимок остаётся доступным для истории и аналитики. Создание отказов заказа подключается при реализации заказов; тесты уже проверяют эту гарантию общего механизма.

До открытия транзакции поставки проверяются доступ, query, ключ, Content-Type, JSON-структура, номер, формат дат, размер коллекции, UUID продуктов, точные положительные количества и независимые от продукта правила полей срока. Неизвестное JSON-поле, не-объект, неверный тип поля или дополнительное JSON-значение дают `400 INVALID_JSON`. Эти ошибки не создают и не перезаписывают ключ: исправленный запрос может использовать прежний UUID.

Проверки, зависящие от БД и времени, остаются после блокировки области и продуктов: активность продукта, целые `pcs`, стандартный срок, будущая приёмка, фактическая просрочка и дубликат номера. Завершённые отказы этих проверок сохраняются. При повторе завершённого запроса проверки текущего состояния не выполняются: исходный `201` воспроизводится даже после истечения срока партии.

Тесты S05-T06 проверяют TTL не менее 24 часов, сохранность активных результатов, удаление истёкшего кеша с сохранением `order_attempts`, движений, аудита и outbox, повторное использование истёкшего ключа, ограничение партии и пропуск заблокированной строки. HTTP-тесты проверяют отсутствие ключа после ранних ошибок и успешный исправленный запрос с тем же UUID; unit-тесты с отсутствующими зависимостями доказывают, что ранние ошибки не обращаются к БД. Отдельный тест проверяет отмену worker во время обращения к БД. Команда запуска — тот же `go test -race -count=1 ./...` с отдельной `SUPPLY_TEST_DATABASE_URL`.

## Список поставок (S06-T01)

`GET /api/v1/supplies` зарегистрирован через `RegisterRoutes`. Handler находится в `internal/handler/supply`, проекция ответа — в `internal/service/supply/list.go`, SQL — в `internal/repository/supply/list.go`. Интерфейсы объявлены в использующих их пакетах; router не импортирует предметный handler, поэтому циклической зависимости нет.

Параметры запроса:

| Параметр | Поведение |
|---|---|
| `search` | Буквальная часть номера без учёта регистра; отсутствие или пустая строка не ограничивают выборку |
| `from` | `created_at >= from`; RFC3339 с timezone |
| `to` | `created_at < to`; RFC3339 с timezone |
| `page` | Положительное целое число; по умолчанию 1 |
| `page_size` | 1–100; по умолчанию 50 |
| `sort` | Единственное значение `-created_at`; применяется и при отсутствии параметра |

Фильтры объединяются через AND. `from > to` даёт `422`, равные границы дают пустой список. SQL использует `created_at`, а дата фактической приёмки `received_at` выводится в элементе ответа. Проценты, подчёркивания и обратный слеш в поиске экранируются; значения передаются параметрами SQL. Запрос с `search=%` ищет номер, содержащий знак процента.

Порядок всегда `created_at DESC, id DESC`, включая записи с одинаковой датой создания. `total` считается после всех фильтров и до `LIMIT/OFFSET`. Счётчик и страница читаются в одной транзакции `REPEATABLE READ READ ONLY`: поставка, добавленная между двумя SELECT, не попадёт только в одну часть ответа. Стабильный порядок не фиксирует снимок между отдельными HTTP-запросами — новая поставка может сдвинуть страницы.

Смещение страницы вычисляется как `int64` с проверкой переполнения. Неизвестные, повторные, пустые числовые или неверно закодированные параметры дают общий `422 VALIDATION_ERROR` до обращения к service. Пустой результат и страница после конца списка возвращают `200`, `items: []`; `total` на странице после конца сохраняет число найденных поставок. `meta` — `{}`.

Каждый элемент — `SupplySummaryDTO`: ID, номер, `created_at`, `received_at`, число исходных строк, автор (`id`, `name`) и `status: received`. Число строк учитывает все партии, включая израсходованные. Даты возвращаются в UTC с сохранением дробных секунд. Поля пользователя с паролями или хешами в проекцию не входят.

Список защищён тем же `RequireSupplyAccess`, что приёмка и детали: требуется действующая сессия и роль admin/manager/storekeeper. Без сессии — `401`, запрещённая роль — `403`. Список проходит существующие request ID, логирование, обработку ошибок, лимит тела и rate limit.

Пример после запуска backend:

```bash
curl --cookie "flagman_session=$SESSION_TOKEN" 'http://api.flagman.localhost/api/v1/supplies?search=104&from=2026-10-01T00:00:00Z&to=2026-11-01T00:00:00Z&page=1&page_size=20&sort=-created_at'
```

Unit-тесты handler проверяют параметры, значения по умолчанию и единый формат ошибок. Интеграционные тесты используют настоящий HTTP-сервер и PostgreSQL с миграциями: поиск и специальные символы, границы дат, пагинацию, равные даты и ID, пустые страницы, структуру ответа и согласованность счётчика с выборкой при конкурентной вставке. Каждый тест создаёт отдельную схему и удаляет её после проверки.

Запуск из `backend` с отдельной тестовой PostgreSQL:

```bash
SUPPLY_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./...
```

Без `SUPPLY_TEST_DATABASE_URL` интеграционные тесты пропускаются; unit-тесты продолжают запускаться.

## Детали поставки (S06-T02)

`GET /api/v1/supplies/{id}` возвращает `200` с `SupplyDetail`: поля сводки поставки, `items` с продуктом и партией каждой исходной строки, `meta.server_time`. Query-параметров у операции нет. Неверный UUID и неизвестный или повреждённый query дают `422 VALIDATION_ERROR` до обращения к БД. Корректный UUID отсутствующей поставки даёт `404 NOT_FOUND`. Ошибка чтения любой части ответа даёт общий `500 INTERNAL_ERROR` без частичных деталей или SQL.

Даты имеют разное назначение:

| Поле | Значение |
|---|---|
| `created_at` | Время создания записи поставки в системе |
| `received_at` | Фактическое время приёмки, сохранённое в поставке |
| `items[].batch.created_at` | Время создания записи конкретной партии |
| `items[].batch.supply.received_at` | Фактическая дата приёмки родительской поставки |

Эти поля читаются независимо и возвращаются в UTC, RFC3339 с сохранением дробных секунд. Например, товар приняли в `09:00`, поставку внесли в систему в `09:05`: `received_at` и `created_at` в ответе сохранят это различие. Поиск по датам и сортировка списка S06-T01 по-прежнему используют `created_at`.

Строки идут по `line_number ASC, id ASC`. Все партии сохраняются в истории поставки: просроченные, полностью израсходованные и партии продуктов, отключённых после приёмки. Две строки с одним продуктом остаются двумя строками. `items_count` равен их общему числу. В продукте возвращаются ID, название, базовая и отображаемая единицы; в партии — ID, связь с поставкой, номер строки, исходное количество и текущий остаток, фактические `produced_at`, `shelf_life_hours`, `expiry_source`, `expires_at`, статус и даты. Количества — точные десятичные строки. Срок партии читается из `batches` и не пересчитывается по изменившемуся стандарту продукта; отсутствующие дата производства и срок в часах возвращаются как `null`.

Service фиксирует одно время `T` перед чтением, выводит его в `meta.server_time` и использует для всех партий. `remaining_seconds = floor(expires_at - T)` — знаковое число секунд; просрочка даже менее секунды даёт `-1`. При нулевом остатке статус `depleted` имеет приоритет. Иначе при `expires_at <= T` статус `expired`, при сроке до `T + expiring_threshold_hours` включительно — `expiring`, позже — `valid`. Порог берётся из настроек ресторана; при отсутствии строки настроек используется 24 часа.

Поставка, автор, настройки, продукты и партии читаются в одной транзакции `REPEATABLE READ READ ONLY`. Конкурентное изменение продукта или остатка между SELECT не смешивает данные разных снимков. Запрос проходит общие HTTP middleware; действующая сессия и роль admin/manager/storekeeper требуются, как и у списка поставок.

Пример:

```bash
curl --cookie "flagman_session=$SESSION_TOKEN" 'http://api.flagman.localhost/api/v1/supplies/<supply-uuid>'
```

Unit-тесты проверяют параметры, общий формат ошибок, единое время запроса и границы статусов. Интеграционные тесты на PostgreSQL проверяют разные даты создания и приёмки, продукты и все партии, точные количества, фактический срок, настройки ресторана, `404`, отказ второго SELECT без частичного ответа и согласованность снимка при конкурентном изменении. Запуск — той же командой с `SUPPLY_TEST_DATABASE_URL`, что для S06-T01.

## Проверки деталей после расхода (S06-T03)

`TestSupplyDetailsNotFoundIntegration` проверяет `404 NOT_FOUND` для неизвестного UUID, нулевого UUID и ID партии вместо ID поставки. Ответ содержит общий JSON ошибки с непустым `request_id`, совпадающим с `X-Request-ID`, и `details: {}`. Данные поставки и SQL в ошибку не попадают. Неверный формат UUID по-прежнему даёт `422`, что проверяется unit-тестом handler.

`TestSupplyDetailsAfterConsumptionIntegration` проверяет настоящий `GET /api/v1/supplies/{id}` на PostgreSQL до расхода и после каждого зафиксированного изменения:

| Шаг | Остаток первой партии | Остаток второй партии | Ожидаемое состояние |
|---|---|---|---|
| Исходная поставка | `3.250` | `2.000` | Обе партии присутствуют |
| Частичный расход `1.125` | `2.125` | `2.000` | Изменился только остаток первой партии |
| Расход оставшихся `2.125` | `0.000` | `2.000` | Первая партия присутствует со статусом `depleted` |
| Расход второй партии `2.000` | `0.000` | `0.000` | Обе партии присутствуют со статусом `depleted`; детали возвращают `200` |

Сценарий запускается для годных, скоро истекающих и просроченных партий. Пока остаток положителен, статус определяется сроком (`valid`, `expiring`, `expired`); при нуле `depleted` имеет приоритет. Исходные количества, ID и порядок строк, продукты, даты создания и приёмки, фактические сроки партий не меняются. После полного расхода поставка также остаётся в списке с `items_count: 2` и `status: received`. Повторное чтение деталей сохраняет зафиксированные остатки.

Операции заказа и списания в текущей рабочей копии ещё не реализованы. Для проверки чтения тестовая фикстура создаёт поступления в журнале, затем в одной транзакции уменьшает остаток и записывает `manual_writeoff` с автором, причиной и остатком после движения. После каждого шага сумма движений сверяется с текущими остатками. Это проверка деталей после зафиксированного расхода; HTTP-операции самого расхода будут проверены при их реализации. Даты сроков строятся от текущего времени, просроченная партия создаётся только тестовой фикстурой.

Запуск новых проверок из `backend`:

```bash
SUPPLY_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./internal/handler/supply \
    -run 'TestSupplyDetails(NotFound|AfterConsumption)Integration'
```

Каждый сценарий использует отдельную схему с миграциями и удаляет её после завершения. Без `SUPPLY_TEST_DATABASE_URL` эти интеграционные проверки пропускаются.

## Выбор продуктов для форм (S07-T01)

`GET /api/v1/products` возвращает список `Product` для выбора продукта в поставке, рецепте и каталоге. Handler находится в `internal/handler/product`, service — в `internal/service/product`, SQL — в `internal/repository/product`. Маршрут подключается через `RegisterProductRoutes` и проходит общие HTTP middleware.

Каждый элемент содержит:

| Поле | Назначение |
|---|---|
| `id`, `name` | Идентификатор для отправки формы и название для выбора |
| `category: {id, name}` | Категория продукта |
| `unit`, `display_unit` | Базовая единица g/ml/pcs и единица отображения g/kg/ml/l/pcs |
| `standard_shelf_life_hours` | Стандартный срок в часах или `null`, если стандарт не задан |
| `target_stock` | Целевой запас в базовой единице: точная десятичная строка или `null` |
| `is_active`, `revision`, `created_at` | Активность, ревизия и дата создания записи в UTC |

Нулевой запас возвращается как `"0.000"`, а не `null`; складские количества в float не преобразуются. Стандартный срок помогает форме подставить значение для расчёта срока партии. Приёмка продолжает самостоятельно проверять продукт и срок на сервере.

Параметры: `search` — буквальная часть имени без учёта регистра, `category_id` — UUID категории, `is_active=true|false|all` (по умолчанию `true`), `sort=name`, `page` и `page_size` (по умолчанию 1 и 50, максимум 100). Фильтры объединяются через AND. `%`, `_` и обратный слеш в поиске экранируются. Порядок — `name ASC, id ASC`; `total` учитывает все фильтры до пагинации. Счётчик, категория и страница читаются в одной транзакции `REPEATABLE READ READ ONLY`, чтобы конкурентное изменение активности не рассогласовало ответ.

Пустая выборка, неизвестная категория и страница за концом возвращают `200` с `items: []`; обёртка всегда содержит `total`, `page`, `page_size`, `meta: {}`. Неизвестные, повторные или неверно закодированные параметры, неверный UUID, сортировка, enum или пагинация дают общий `422 VALIDATION_ERROR`. Техническая ошибка даёт `500 INTERNAL_ERROR` без SQL и частичных данных.

Чтение доступно admin, manager, storekeeper и order_operator с действующей сессией `flagman_session`. Без сессии, с истёкшей/отозванной сессией или отключённым пользователем — `401`. Запрещённая роль — `403`. GET не требует CSRF. Разрешение оператору читать продукты не даёт ему доступа к поставкам.

Пример:

```bash
curl --cookie "flagman_session=$SESSION_TOKEN" \
  'http://api.flagman.localhost/api/v1/products?search=моцарелла&page=1&page_size=20'
```

Unit-тесты проверяют параметры до обращения к service, активность и пагинацию по умолчанию, пустой ответ и безопасные ошибки. Интеграционные тесты с настоящими миграциями PostgreSQL проверяют поля для форм, единицы, точность большого и дробного запаса, `null` и ноль, фильтры, поиск специальных символов, страницы, роли, отозванную сессию, SQL-ошибку и общий снимок при конкурентном отключении продукта.

Запуск из `backend` на отдельной тестовой PostgreSQL:

```bash
PRODUCT_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./internal/handler/product
```

Без `PRODUCT_TEST_DATABASE_URL` интеграционные тесты продуктов пропускаются. Для полного прогона, включая S05/S06, дополнительно задаётся `SUPPLY_TEST_DATABASE_URL`. Каждый сценарий создаёт отдельную тестовую схему и удаляет её после проверки.

## Агрегаты партий в InventoryItem (S07-T02)

`GET /api/v1/inventory` возвращает склад по продуктам, включая продукты без партий и неактивные продукты: отключение продукта не скрывает его физический остаток. Используется та же архитектура `handler/inventory` → `service/inventory` → `repository/inventory`. Маршрут доступен всем четырём ролям с действующей сессией `flagman_session`.

Все расчёты ответа используют один момент `T = meta.server_time` в UTC. Настройки, счётчики, страница и проблемные партии читаются в одной транзакции `REPEATABLE READ READ ONLY`. Порог истечения берётся из `restaurant_settings.expiring_threshold_hours`; без строки настроек используется 24 часа. Фактический `batches.expires_at` не пересчитывается по текущему стандартному сроку продукта.

| Поле | Расчёт по `remaining_quantity` |
|---|---|
| `physical_quantity` | Сумма всех текущих остатков |
| `available_quantity` | Сумма остатков при `expires_at > T` |
| `expiring_quantity` | Сумма остатков при `T < expires_at <= T + порог` |
| `expired_quantity` | Сумма остатков при `expires_at <= T` |
| `nearest_expires_at` | Минимальный срок годной партии с положительным остатком; иначе `null` |
| `batches_count` | Число партий с положительным остатком, включая просроченные |
| `remaining_seconds` | Округлённое вниз число секунд до ближайшего годного срока; иначе `null` |
| `deficit_quantity` | `max(target_stock - available_quantity, 0)`; без целевого запаса — `null` |

`physical_quantity = available_quantity + expired_quantity`, а `expiring_quantity` входит в `available_quantity`. Полностью израсходованные партии не влияют на ближайший срок, число партий и список проблем. У продукта без остатка количества — `"0.000"`, число партий — 0. Агрегаты возвращаются точными десятичными строками с тремя знаками после точки: сумма может превышать максимум `numeric(14,3)` отдельной партии. Приёмка сохраняет прежний предел количества одной строки.

Например, годная партия 1000 г, истекающая партия 500 г и просроченная партия 200 г дают `available="1500.000"`, `expiring="500.000"`, `expired="200.000"`, `physical="1700.000"`, `batches_count=3`. Истёкший срок сам по себе не списывает физический остаток. Частичный или полный расход меняет агрегаты при следующем чтении.

Флаги `has_expiring`, `has_expired`, `is_out_of_stock` могут пересекаться. `is_out_of_stock` означает нулевой доступный остаток, даже если есть просрочка. Основной `status` выбирается по приоритету `expired`, `expiring`, `normal`, `out_of_stock`.

Параметры: `search`, `category_id`, `filter=all|expiring|expired|out_of_stock|deficit`, `sort=name|nearest_expires_at`, `page`, `page_size`. По умолчанию — `all`, `name`, страница 1 и размер 50; максимум 100. Поиск буквальный, без учёта регистра. Последний критерий сортировки — ID; при сортировке по сроку `null` идёт последним. Неверные, неизвестные и повторные параметры дают `422` до открытия транзакции.

Обёртка содержит `items`, `total`, `page`, `page_size`, `meta.server_time`, `counts`, `attention_batches`, `attention_total`. `counts` учитывает поиск и категорию, но игнорирует `filter` и пагинацию; пересекающиеся признаки считаются независимо. `attention_batches` содержит до 20 ненулевых просроченных или истекающих партий в том же поиске/категории, независимо от `filter` и страницы; порядок — `expires_at ASC, id ASC`. `attention_total` — полное число таких партий. Для просрочки `remaining_seconds` может быть отрицательным. Пустые массивы возвращаются как `[]`, отсутствующие сроки и запасы — явными `null`.

```bash
curl --cookie "flagman_session=$SESSION_TOKEN" \
  'http://api.flagman.localhost/api/v1/inventory?filter=expiring&sort=nearest_expires_at'
```

Проверки покрывают равенство сроку и порогу истечения, просрочку на микросекунду, точные большие суммы, отсутствующие и неактивные продукты, целевой запас `null`/ноль, пересекающиеся признаки, частичный и полный расход с согласованным журналом, фильтры и страницы, предел проблемных партий, доступ, безопасную ошибку позднего SQL-запроса и единый снимок при конкурентном расходе.

Запуск из `backend` на отдельной тестовой PostgreSQL:

```bash
INVENTORY_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./internal/service/inventory ./internal/handler/inventory
```

Без `INVENTORY_TEST_DATABASE_URL` интеграционные проверки склада пропускаются. Для полного прогона `./...` с проверками поставок и продуктов дополнительно задаются `SUPPLY_TEST_DATABASE_URL` и `PRODUCT_TEST_DATABASE_URL`. Тесты создают отдельные схемы с настоящими миграциями и удаляют их после завершения.

## Поиск, фильтры, счётчики и проблемные партии (S07-T03)

Функциональность подключена к `GET /api/v1/inventory` вместе с агрегатами S07-T02. В S07-T03 добавлены отдельные интеграционные проверки контракта. `search` ищет буквальную часть имени без учёта регистра, включая кириллицу; `category_id` ограничивает категорию. Эти условия объединяются через AND и применяются к продуктам, счётчикам и проблемным партиям.

Выбранный `filter` проверяет точные количества, независимо от основного бейджа `status`:

| Фильтр | Условие |
|---|---|
| `all` | Все продукты в области поиска и категории |
| `expiring` | `expiring_quantity > 0` |
| `expired` | `expired_quantity > 0` |
| `out_of_stock` | `available_quantity = 0` |
| `deficit` | `deficit_quantity > 0`; `null` и ноль не подходят |

Например, моцарелла с 2 г истекающего годного остатка и 1 г просрочки имеет `status="expired"`, но попадает и в `expired`, и в `expiring`. Сливки только с просроченным остатком тоже имеют `status="expired"`, при этом входят в `out_of_stock`. Продукт без партий входит в `out_of_stock`; в `deficit` он входит только при положительном целевом запасе.

`total` соответствует выбранному фильтру до пагинации. `counts` показывает все независимые счётчики для поиска и категории, игнорируя выбранный фильтр и страницу. Поэтому сумма счётчиков отдельных признаков не обязана равняться `counts.all`.

`attention_batches` тоже игнорирует выбранный фильтр и страницу: это первые 20 проблемных партий в области поиска и категории по `expires_at ASC, id ASC`. `attention_total` считает партии, а не продукты. Только партии с положительным текущим остатком и просроченным либо истекающим сроком входят в этот список. Статус, срок и оставшиеся секунды определяются для каждой партии отдельно; строка содержит ID продукта и поставки, номер поставки, номер строки, единицу и фактический остаток.

Даже при `items: []` из-за выбранного фильтра или страницы за концом `counts` и `attention_batches` остаются заполненными, если в области поиска и категории есть соответствующие продукты и партии. При пустой области все счётчики равны нулю, массивы — `[]`.

Проверки S07-T03 находятся в `internal/service/inventory/filters_integration_test.go`: они проверяют конкретные ID в пересекающихся фильтрах, все значения счётчиков, поиск кириллицы вместе с категорией, пустую страницу и пустой фильтр, независимость проблемных партий от страницы/фильтра, сортировку по собственному сроку партии и остаток после частичного расхода. Ограничение 20 партий и сортировка одинаковых сроков по ID проверяются существующими тестами склада. Запуск — команда для `INVENTORY_TEST_DATABASE_URL` из раздела S07-T02.

## Список партий продукта (S07-T04)

`GET /api/v1/products/{id}/batches` возвращает `Batch` данного продукта: ID партии и продукта, базовую единицу, ссылку на поставку с номером и фактическим `received_at`, номер строки, исходное и текущее количества, факты расчёта срока, фактический `expires_at`, оставшиеся секунды, статус и `created_at` записи партии. Количества — точные десятичные строки; даты — UTC. Партии отключённых продуктов доступны.

Маршрут реализован в `handler/batch` → `service/batch` → `repository/batch` и доступен всем четырём ролям с действующей сессией `flagman_session`. Неверный UUID продукта или параметров — `422`; корректный UUID отсутствующего продукта — `404`. Существующий продукт без подходящих партий возвращает `200` с `items: []`.

| Параметр | Поведение |
|---|---|
| `status` отсутствует | Все партии с положительным остатком, включая просроченные |
| `status=all` | Все партии, включая израсходованные |
| `status=valid|expiring|expired|depleted` | Партии с соответствующим текущим статусом |
| `supply_id` | Ограничение одной поставкой; применяется вместе со статусом |
| `sort=expires_at` | По умолчанию: `expires_at ASC, id ASC` |
| `sort=-created_at` | `created_at DESC, id ASC` |
| `page`, `page_size` | По умолчанию 1 и 50; размер до 100 |

Статус, фильтрация и `remaining_seconds` используют одно время `T = meta.server_time`. Проверка существования продукта, чтение порога ресторана, счётчик и страница выполняются в одной транзакции `REPEATABLE READ READ ONLY`. `total` учитывает статус и поставку до пагинации. Неизвестная поставка в фильтре и страница за концом дают пустой массив. Неизвестные, повторные или неверно закодированные параметры дают `422` до транзакции.

| Условие | Статус |
|---|---|
| `remaining_quantity = 0` | `depleted`, независимо от срока |
| Положительный остаток, `expires_at <= T` | `expired` |
| Положительный остаток, `T < expires_at <= T + порог` | `expiring` |
| Положительный остаток, срок позже порога | `valid` |

Порог — `restaurant_settings.expiring_threshold_hours`; без строки настроек — 24 часа. Фактический срок партии не заменяется текущим стандартным сроком продукта. `remaining_seconds = floor((expires_at - T) / 1s)` — знаковое число, в том числе у израсходованных партий. На точной границе `expires_at = T` положительный остаток имеет статус `expired` и 0 секунд; нулевой — `depleted` и тоже 0 секунд. Срок на микросекунду раньше даёт -1 секунду; на микросекунду позже — 0 секунд, но статус `expiring`. Статус определяется самим сроком, а не округлёнными секундами.

Расчёт статуса и секунд в `service/batch/state.go` используется также деталями поставки; расчёт секунд — агрегатами склада. Ошибка чтения или завершения транзакции даёт полный безопасный ответ ошибки, без частичной страницы.

```bash
curl --cookie "flagman_session=$SESSION_TOKEN" \
  "http://api.flagman.localhost/api/v1/products/$PRODUCT_ID/batches?status=all&sort=expires_at"
```

Проверки покрывают все статусы, точное равенство сроку, микросекундные границы и включительный порог 24/48 часов, приоритет `depleted` до/на/после срока, точные количества и nullable-факты расчётного срока, фильтры, обе сортировки и порядок по ID, страницы, отсутствие продукта, отключённый продукт, все роли, безопасную ошибку SQL, частичный/полный расход с согласованным журналом и конкурентное списание между счётчиком и страницей.

Запуск из `backend` на отдельной тестовой PostgreSQL:

```bash
BATCH_TEST_DATABASE_URL='postgres://<user>:<password>@127.0.0.1:<test-port>/<test-db>?sslmode=disable' \
  GIN_MODE=release go test -race -count=1 ./internal/service/batch ./internal/handler/batch
```

Без `BATCH_TEST_DATABASE_URL` интеграционные проверки списка партий пропускаются. Каждый сценарий создаёт отдельную схему с миграциями и удаляет её после завершения. Для полного прогона `./...` с предыдущими интеграционными проверками также задаются `SUPPLY_TEST_DATABASE_URL`, `PRODUCT_TEST_DATABASE_URL` и `INVENTORY_TEST_DATABASE_URL`.
