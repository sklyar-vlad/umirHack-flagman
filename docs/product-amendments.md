# Поправки после защиты: аналитика, предложения и внешние поставки

## Что изменено

В основе учёта остался неизменяемый журнал `stock_movements`. Новый отчёт
`/analytics` и `/analytics/product-flow` показывает для каждой пары «продукт +
историческая единица» фактический приход в поставках, расход ингредиентов в
успешных заказах, просрочку, ручные списания и сумму списаний. Период задаётся
как `[from, to)` в часовом поясе ресторана. Названия берутся из истории операций.
Разные единицы и разные продукты не складываются в один итог.

Ожидающая внешняя поставка не участвует в остатках и аналитике. После частичной
приёмки учитывается только принятое количество. Отклонённые заказы не считаются
расходом. «Ушло в заказы» означает фактическое потребление партий по рецептам,
а не число проданных порций.

Для роли `order_operator` реализован экран «Меню» (`/dishes`) с составом,
доступностью, количеством порций и добавлением блюда в заказ. В навигации видны
«Меню» и «Горячие предложения». Роль в интерфейсе обозначена как
«Официант / оператор заказов»; существующие коды ролей и учётные записи сохранены.
Автор принятого заказа по-прежнему записывается в `orders.created_by`.

Менеджер и администратор могут добавить доступное блюдо в горячие предложения
из меню, изменить рекомендацию, скрыть публикацию или оставить ручной выбор.
Ручное предложение не требует истекающей партии, но всегда требует доступных
ингредиентов. Автоматический расчёт FEFO и приоритетов сохранён. Официант
получает только опубликованные предложения и не может изменять их настройки.
Это правило действует и в `/dashboard`. Изменения поступают другим клиентам
через существующий SSE. Ревизия защищает от перезаписи чужого изменения.

## Внешний сервис

`/admin/integrations` позволяет администратору создать именованный API-токен
для поставщика и отозвать его. Секрет выдаётся однократно и не сохраняется в
браузерном хранилище; в PostgreSQL хранится только SHA-256. Токен перестаёт
работать также при отключении владельца или потере им роли администратора.
Создание продуктов и отправка заявок не дают права принимать поставки,
редактировать существующий каталог, читать заказы или списывать продукты.

Отдельный клиент поставщика расположен в `supplier-demo/`. Это независимая
статическая веб-страница с реальными запросами к API приложения. Она умеет:

- подключаться по адресу приложения и Bearer-токену;
- читать продукты и категории;
- создавать продукт, который появляется в основном приложении;
- отправлять многострочную накладную со сроками и количеством;
- повторять тот же документ с тем же внешним ID без дублирования.

Клиент использует `credentials: omit`. CORS для `/api/v1/integration/` допускает
независимый origin и заголовок Authorization. Правила cookie/CSRF/CORS обычного
приложения сохранены. Привязка внешних ID действует внутри одного токена.
Повтор с тем же ID и другим содержимым возвращает 409; после замены токена
клиенту нужно согласовать новые внешние идентификаторы.

API внешнего сервиса:

| Метод | Путь после `/api/v1` | Назначение |
|---|---|---|
| GET | `/integration/products` | Продукты с обычной пагинацией и фильтрами |
| GET | `/integration/product-categories` | Категории |
| POST | `/integration/products` | Создание продукта с `external_id` |
| POST | `/integration/supplies` | Отправка накладной в ожидание |

У всех этих операций авторизация `Authorization: Bearer flagman_…`. Пользовательская
cookie не заменяет этот токен. Формат полностью описан в
[OpenAPI](../backend/docs/openapi.yaml).

Пример тела создания продукта:

```json
{
  "external_id": "supplier-product-42",
  "product": {
    "name": "Томаты черри",
    "category_id": "<UUID существующей категории>",
    "unit": "g",
    "display_unit": "kg"
  }
}
```

Пример заявки на поставку:

```json
{
  "external_id": "supplier-delivery-1042",
  "number": "П-1042",
  "items": [
    {
      "product_id": "<UUID продукта в Кладовой>",
      "quantity": "1200.000",
      "expires_at": "2030-01-01T12:00:00+03:00"
    }
  ]
}
```

Количество передаётся строкой в базовых единицах g/ml/pcs. Штуки — только целые;
для g/ml разрешено до трёх десятичных знаков. Срок обязательно задаётся с зоной.
Продукт должен существовать и быть активным. Внешняя поставка не резервирует
и не зачисляет продукты сама.

## Приёмка

«Поставки → Входящие поставки» (`/supplies/incoming`) доступна администратору,
менеджеру и кладовщику. Статусы: `pending` (ожидание), `partial` (частично),
`received` (полностью). Пока сотрудник не подтверждает приёмку, заявка остаётся
в ожидании. В форме можно указать количество по каждой строке; ноль оставляет
строку на ожидании. Повторная приёмка добавляется к уже принятому количеству.

На каждую подтверждённую часть создаётся обычная поставка с партиями и движениями.
Её номер `EXT-<ID входящей поставки>-<ревизия>` уникален; исходный номер накладной
отображается во входящем документе. Ссылки на все приёмки остаются в документе.
Сотрудник фиксируется в обычной поставке, действия — в журнале аудита.

`POST /incoming-supplies/{id}/accept` принимает:

```json
{
  "expected_revision": 1,
  "items": [
    {"id": "<ID строки входящего документа>", "quantity": "400.000"}
  ]
}
```

Строки и документ блокируются на время операции. Склад, партии, движения,
аудит, outbox, количество принятого и ревизия фиксируются одной транзакцией.
Конкурентная приёмка старой ревизии возвращает 409. Принять больше остатка,
просроченный или отключённый продукт нельзя. После потери ответа нужно
обновить очередь и проверить уже принятые количества перед повтором.
Продукту, связанному с входящим документом, нельзя менять базовую единицу.

SSE `supplies.incoming_changed` обновляет очередь у принимающих сотрудников.
Подтверждённая приёмка отправляет обычное `inventory.changed`, обновляя склад,
меню, стоп-лист, предложения и отчёт движения продуктов.

## Запуск и демонстрация

1. На машине приложения из корня проекта выполните `task up`: он собирает
   frontend/backend и применяет миграции, включая `00012_integrations_and_offers`.
2. Войдите администратором, откройте «Админ-панель → Интеграции», создайте и
   скопируйте токен.
3. Запустите независимую страницу поставщика на своём компьютере:

   ```bash
   python3 -m http.server 5184 --bind 127.0.0.1 --directory supplier-demo
   ```

   Откройте `http://127.0.0.1:5184`, укажите адрес приложения и API-токен.
   Альтернативный запуск через Docker из корня:

   ```bash
   docker compose -f infrastructure/compose.supplier.yaml up -d --build
   ```

4. Создайте продукт и отправьте поставку на 1200 г.
5. В приложении примите 400 г. Проверьте статус «Принята частично», склад и
   аналитику. Оставшиеся 800 г всё ещё ожидают приёмки.
6. Примите остаток, оформите заказ и ручное списание. Сверьте три колонки
   «Пришло в поставках», «Ушло в заказы», «Всего списано».
7. Менеджером откройте меню, добавьте блюдо в предложения и задайте текст.
   В другой сессии официант увидит предложение. После скрытия оно исчезнет.

Проверки: `bash scripts/integration-checks.sh backend` поднимает временную
локальную PostgreSQL, `npm --prefix frontend run test:production` — изолированные
nginx/backend/PostgreSQL и Playwright. Новые браузерные сценарии находятся в
`frontend/tests/production/amendments.pw.ts`; они работают с настоящим API,
включая отдельный origin поставщика, частичную приёмку, заказ, списание,
публикацию для официанта и скриншоты desktop/mobile.

Существующий внешний сервис не подключён: его контракт не предоставлен.
Демонстрационный клиент использует новый рабочий интеграционный API и может
быть заменён реальным поставщиком без изменения механизма приёмки.
